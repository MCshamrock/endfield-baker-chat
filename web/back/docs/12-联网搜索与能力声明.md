# 联网搜索：为什么不做，以及怎么告诉客户端

> 2026-11-17。老后端有「联网搜索」这条知识源（`use_rag=false` / `force_search=true`）。
> 新后端**不做**。这份文档讲清楚决定、代价和声明方式。

## 1. 现状

| 入口 | 新后端行为 |
|---|---|
| 老客户端 `/chat` 带 `use_rag=false` | **忽略**，照常用世界书回答；只记一条 info 日志 |
| 老客户端 `/chat` 带 `force_search=true` | 同上 |
| 新客户端 | 从 `/v1/meta` 的 `capabilities.web_search=false` 知道没这能力，不显示按钮 |
| 老群聊 `/group/reply` 带 `use_rag` | 忽略（群聊本来就没接搜索） |

**没有报错、没有假装联网。** 假装比不支持更糟：用户以为查了资料，其实模型在编。

## 2. 为什么不做

1. **世界书已经覆盖设定类问题**：147 条（术语/人物/地点/事件/规则）是按终末地整理过的，
   比搜索引擎抓来的二手内容准。
2. **角色扮演里联网经常帮倒忙**：模型一旦进入"根据资料显示……"的口吻，人设当场就散了。
   老后端的提示词里专门写了一条"不得说不知道来否认情报"，就是在补这个洞。
3. **成本**：搜索 API 要 key、要计费、要处理来源引用与时效，还要防"搜到同人二设当官方设定"。

## 3. 怎么做声明的

`/v1/meta` 同时给两个形状：

```json
{
  "caps": ["conversations", "messages", "…", "memory", "suggestions", "think"],
  "capabilities": {
    "web_search": false,
    "worldbook": true,
    "suggestions": true,
    "group": true,
    "group_weighted": true,
    "continue": true,
    "think": true,
    "reasoning_stored": true,
    "memory": true,
    "import": true,
    "login": true,
    "attachments": true,
    "stream": true
  }
}
```

- `caps`（列表）是老形状，**一个字段都没动**，老客户端不受影响；
- `capabilities`（布尔字典）是新加的，它能表达"明确不支持"——列表里没有 `web_search`，
  客户端只能猜是"没实现"还是"忘了写"，布尔值不给人猜的空间。

## 4. 什么时候该回头看这件事

日志里搜这条：

```
老客户端请求了联网搜索（force_search=True use_rag=False）：新后端不支持，已按世界书回答
```

如果这条在真实流量里**频繁出现**，说明有人真的在依赖它，那时再评估：
要么做，要么在客户端明说"这个按钮已经没有了"。

现在先攒样本 —— 不然就是凭感觉决定要不要写一个几千行的子系统。
