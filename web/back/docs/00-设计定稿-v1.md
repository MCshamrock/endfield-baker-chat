# BakerAI 新后端 · 设计定稿 v1

> 2026-11-15
> 范围：**只做后端**。前端（`web/front`、`cleint`）来适配这套契约，不为前端妥协状态归属。
> 本刀（切片 1）= **MySQL 骨架 + 13 张表 + 会话/消息/幂等**。不出话、不检索、不群聊、不做登录。
> **最高约束：代码可读性优先于"写得快/写得巧"。** 见 §4，那是硬规矩，不是建议。

## 1. 边界（先划清，别越界）

| 做 | 不做 |
|---|---|
| 服务端持有会话/消息/摘要/用量的真相 | 渲染、气泡几何、分段播放节奏 |
| 定 `/v1` 契约，并保留老 `/chat` 兼容层 | 为老前端的字段奇怪之处"让步"（垫片在服务端翻译） |
| MySQL 单实例 + 单进程 | Redis / Celery / Docker / 向量库 |
| 设备匿名 token（登录后置） | 邮箱验证码、第三方登录（v1.1，表已预留） |

一句话：**状态在谁手里，逻辑就在谁手里。客户端只发"会话指针 + 新事件 + 幂等键"。**

## 2. 技术栈定版

| 层 | 选型 | 为什么（一句话） |
|---|---|---|
| 运行时 | Python **3.12–3.14**（本地 3.12.12 开发；服务器 3.14.4 已实测跑过全部测试） | 两个版本都验过，`requires-python` 写 `>=3.12,<3.15` |
| Web | FastAPI + uvicorn，`workers=1` | key 状态在进程内；多 worker 会让粘性分裂 |
| DB | **MySQL 8.4.13 Windows 便携版**（`127.0.0.1:3307`，程序+数据都在 `_runtime/mysql`） | 与服务器**同版本**；便携版是为了"一个文件都不出文件夹"（WSL 方案受 socket 限制，见 §8 末尾） |
| ORM | SQLAlchemy 2.x，**同步**，`pymysql` 驱动 | 原型已验；别为 async 引新坑（但有例外，见 §7.5） |
| 迁移 | **手写 `schema/NNN_*.sql` + 20 行执行器**（备选 Alembic） | 只有一个部署目标，自动生成的迁移反而难读。取舍理由见 §11 |
| 校验 | pydantic v2 | FastAPI 自带，报错信息直接可用 |
| 日志 | 标准库 `logging` + JSON + `request_id` | 不引 structlog |
| 测试 | pytest + httpx（ASGI 直连，不起端口） | 一个命令验完整刀 |
| 进程 | systemd **user** 单元（线上） | 服务器已在用 |

## 4. 可读性公约（10 条，带工具兜底）

"代码高可读性"不能靠自觉，要落成可检查的东西：

| # | 规矩 | 怎么保证 |
|---|---|---|
| 1 | **命名用完整英文单词**：`conversation_id` 不写 `cid`，`visible_scope` 不写 `sc`。函数名是动词短语 `ensure_device_owns_conversation`。**库名/表名/列名/索引名一律全小写下划线**（理由见 §8.2） | code review + ruff N 规则 |
| 2 | **注释写中文、讲"为什么"**：文件顶部一段说明；每个函数一行 docstring 说"做什么/返回什么"；**凡是踩过坑的地方（时区、seq 分配、幂等）必须 3–5 行注释讲清后果** | 没有 docstring 的公开函数直接不收 |
| 3 | **函数不超过 40 行、嵌套不超过 3 层** | ruff `C901` 复杂度上限 8 |
| 4 | **单个文件不超过 300 行** | 超了就是该拆模块的信号 |
| 5 | **显式优于取巧**：不用元类、不用装饰器做业务逻辑、不 `**kwargs` 透传业务参数、不写嵌套三元 | ruff `BLE`/`SIM` 规则集 |
| 6 | **类型标注全量**：`from __future__ import annotations`，每个函数签名标类型；请求/响应都用 pydantic 模型，不手搓 dict | pyright basic |
| 7 | **错误只有一条路**：业务抛 `AppError(code, http_status, 中文话)`，出口统一转 JSON；路由里禁止散落 `try/except` 吞异常 | 只有 `main.py` 一个异常处理器 |
| 8 | **一屏能读完一个实体**：`models.py` 里每张表紧挨着它的字段注释，不跳文件 | 人工审 |
| 9 | **不留死代码**：注释掉的旧实现一律删除；`TODO` 必须带日期和这行代码解决什么问题 | `grep TODO` 进 CI |
| 10 | **SQL 与 Python 分离**：所有查询在 `repos/`，路由层零 SQL | 目录约定 + review |

工具：`ruff`（line-length 100，规则 `E,F,W,I,N,B,BLE,SIM,C4,C901`）+ `pyright`（basic）+ `pytest`。
一条命令全过：`bash scripts/check.sh`（ruff → pyright → pytest，任一失败即非 0 退出）。

> 说明：这 10 条会让代码行数比"能跑就行"多 20% 左右。**这钱值得花**——上一个后端 7563 行里，最大的 `common.py` 2110 行，没人敢动，就是省这 20% 省出来的。

## 5. 表结构（13 张，MySQL 8.4）

### 5.1 全局约定

| 项 | 约定 | 为什么 |
|---|---|---|
| 字符集 | 库/表/连接全 `utf8mb4`；排序 `utf8mb4_0900_ai_ci` | 中文 + emoji；`_ci` 大小写不敏感 |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 索引小、顺序写快 |
| 对外 id | `public_id CHAR(32)`（uuid4 hex） | 不把自增 id 暴露给前端，防遍历 |
| 时间 | `DATETIME(6)`，**全部存 UTC**；连接固定 `time_zone='+00:00'`；**不用 `TIMESTAMP`** | TIMESTAMP 有 2038 + 隐式时区转换两个坑 |
| 布尔 | `TINYINT(1)` | MySQL 没有真 bool |
| 长文本 | `MEDIUMTEXT`（≤16MB） | 消息/提示词 |
| 软删 | `deleted_at DATETIME(6) NULL` | 只给会话用；消息不软删 |

### 5.2 `users` —— 账号（v1 只预留，不做登录）

```sql
CREATE TABLE users (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id     CHAR(32)        NOT NULL,
  login_type    ENUM('none','email','qq') NOT NULL DEFAULT 'none',
  login_id      VARCHAR(190)    NULL COMMENT '邮箱等；guest 为 NULL',
  pass_hash     VARCHAR(255)    NULL,
  display_name  VARCHAR(64)     NOT NULL DEFAULT '',
  status        ENUM('active','disabled') NOT NULL DEFAULT 'active',
  created_at    DATETIME(6)     NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  last_seen_at  DATETIME(6)     NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_users_public_id (public_id),
  UNIQUE KEY uk_users_login_id (login_type, login_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='账号。v1 不启用登录，表先建好，device 可挂到 user 名下';
```

> `UNIQUE(login_type, login_id)` 里 MySQL 允许多个 NULL——访客不登录不会互相撞。

### 5.3 `devices` —— 设备（真正在用的身份）

```sql
CREATE TABLE devices (
  id            BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id     CHAR(32)     NOT NULL,
  token_hash    CHAR(64)     NOT NULL COMMENT 'token 的 sha256；明文只在注册时返回一次',
  owner_user_id BIGINT UNSIGNED NULL COMMENT 'NULL = 访客；登录后挂到 user',
  platform      VARCHAR(32)  NOT NULL DEFAULT 'unknown' COMMENT 'android/windows/web',
  app_ver       VARCHAR(32)  NOT NULL DEFAULT '',
  app_build     INT          NOT NULL DEFAULT 0,
  model         VARCHAR(64)  NOT NULL DEFAULT '',
  os_ver        VARCHAR(32)  NOT NULL DEFAULT '',
  tz            VARCHAR(64)  NOT NULL DEFAULT '',
  locale        VARCHAR(16)  NOT NULL DEFAULT '',
  created_at    DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  last_seen_at  DATETIME(6)  NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_devices_public_id (public_id),
  UNIQUE KEY uk_devices_token_hash (token_hash),
  KEY ix_devices_owner (owner_user_id),
  CONSTRAINT fk_devices_user FOREIGN KEY (owner_user_id) REFERENCES users (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='设备。token 只存哈希；换机迁移靠绑定码（后续）';
```

### 5.4 `characters` / `character_prompts` —— 角色与提示词

```sql
CREATE TABLE characters (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  slug        VARCHAR(64)  NOT NULL COMMENT '稳定英文 id，前端不再硬编码角色表',
  name        VARCHAR(64)  NOT NULL COMMENT '中文名',
  avatar      VARCHAR(255) NOT NULL DEFAULT '',
  attribute   VARCHAR(32)  NOT NULL DEFAULT '',
  sort_order  INT          NOT NULL DEFAULT 0,
  enabled     TINYINT(1)   NOT NULL DEFAULT 1,
  PRIMARY KEY (id),
  UNIQUE KEY uk_characters_slug (slug),
  KEY ix_characters_enabled (enabled, sort_order)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='角色。服务端权威，客户端只缓存';

CREATE TABLE character_prompts (
  id           BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  character_id BIGINT UNSIGNED NOT NULL,
  ver          INT          NOT NULL COMMENT '版本号，改提示词就 +1，不原地覆盖',
  body         MEDIUMTEXT   NOT NULL COMMENT '自然语言人设，约 5000 字',
  active       TINYINT(1)   NOT NULL DEFAULT 0,
  created_at   DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_prompts_char_ver (character_id, ver),
  KEY ix_prompts_active (character_id, active),
  CONSTRAINT fk_prompts_char FOREIGN KEY (character_id) REFERENCES characters (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='角色提示词，按版本存。改人设不覆盖历史，出问题能回退';
```

### 5.5 `conversations` —— 会话（本刀的核心）

```sql
CREATE TABLE conversations (
  id             BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id      CHAR(32)     NOT NULL,
  device_id      BIGINT UNSIGNED NOT NULL COMMENT '归属设备（访客也有）',
  user_id        BIGINT UNSIGNED NULL COMMENT '登录后才有',
  character_id   BIGINT UNSIGNED NULL COMMENT '单聊的角色；群聊为 NULL',
  mode           ENUM('single','group') NOT NULL DEFAULT 'single',
  title          VARCHAR(120) NOT NULL DEFAULT '',
  next_seq       BIGINT UNSIGNED NOT NULL DEFAULT 0 COMMENT '下一个消息序号；分配时 SELECT FOR UPDATE 锁行',
  api_key_id     BIGINT UNSIGNED NULL COMMENT 'key 亲和绑定：这个会话固定用哪把 key',
  summary_head   TEXT         NULL COMMENT '摘要头（最近一次的压缩结果引用）',
  created_at     DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  last_active_at DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  deleted_at     DATETIME(6)  NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_conv_public_id (public_id),
  KEY ix_conv_device_active (device_id, last_active_at),
  KEY ix_conv_user (user_id, last_active_at),
  CONSTRAINT fk_conv_device FOREIGN KEY (device_id) REFERENCES devices (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='会话。唯一真相在服务端；客户端只拿 public_id 当指针';
```

### 5.6 `conversation_members` —— 群聊成员（第 13 张，本刀只建表不写逻辑）

```sql
CREATE TABLE conversation_members (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  conversation_id BIGINT UNSIGNED NOT NULL,
  character_id    BIGINT UNSIGNED NOT NULL,
  ord             INT          NOT NULL COMMENT '发言顺序，从 0 开始',
  role            ENUM('ai','player') NOT NULL DEFAULT 'ai',
  PRIMARY KEY (id),
  UNIQUE KEY uk_members_conv_ord (conversation_id, ord),
  CONSTRAINT fk_members_conv FOREIGN KEY (conversation_id) REFERENCES conversations (id),
  CONSTRAINT fk_members_char FOREIGN KEY (character_id) REFERENCES characters (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='群聊成员。单聊不用；切片 8 才读写';
```

### 5.7 `messages` —— 消息（幂等的落点）

```sql
CREATE TABLE messages (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  conversation_id BIGINT UNSIGNED NOT NULL,
  seq             BIGINT UNSIGNED NOT NULL COMMENT '会话内序号，从 1 连续递增',
  client_msg_id   VARCHAR(64)  NOT NULL COMMENT '幂等键；assistant 用 a:{seq} 填，禁止空串（空串会撞唯一键）',
  side            ENUM('user','assistant','system') NOT NULL,
  speaker         VARCHAR(64)  NOT NULL DEFAULT '' COMMENT '玩家代演的角色名（R-001）；空 = 用户本人',
  text            MEDIUMTEXT   NOT NULL,
  attachment_id   BIGINT UNSIGNED NULL,
  visible_scope   ENUM('private','group') NOT NULL DEFAULT 'group' COMMENT '群聊可见性，防串台',
  mood            VARCHAR(32)  NOT NULL DEFAULT '',
  tokens          INT          NOT NULL DEFAULT 0,
  origin          ENUM('v1','legacy') NOT NULL DEFAULT 'v1' COMMENT 'legacy = 老 /chat 垫片写入',
  created_at      DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_msg_conv_seq (conversation_id, seq),
  UNIQUE KEY uk_msg_conv_client (conversation_id, client_msg_id),
  KEY ix_msg_conv_id (conversation_id, id),
  CONSTRAINT fk_msg_conv FOREIGN KEY (conversation_id) REFERENCES conversations (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='消息。两个唯一键就是全部幂等保证，不靠应用层判重';
```

### 5.8 `attachments` / `summaries` / `usage_events`

```sql
CREATE TABLE attachments (
  id         BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  public_id  CHAR(32)     NOT NULL,
  sha256     CHAR(64)     NOT NULL COMMENT '按内容去重',
  mime       VARCHAR(64)  NOT NULL DEFAULT '',
  bytes      BIGINT UNSIGNED NOT NULL DEFAULT 0,
  width      INT          NOT NULL DEFAULT 0,
  height     INT          NOT NULL DEFAULT 0,
  path       VARCHAR(255) NOT NULL DEFAULT '' COMMENT '相对存储根路径',
  created_at DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uk_att_public_id (public_id),
  UNIQUE KEY uk_att_sha256 (sha256)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_0900_ai_ci
  COMMENT='附件。图片不再 base64 塞进消息体';

CREATE TABLE summaries (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  conversation_id BIGINT UNSIGNED NOT NULL,
  ver             INT          NOT NULL COMMENT '第几版摘要，可回滚',
  body            JSON         NOT NULL COMMENT '{memory, plot, state, timeline} 结构化，给 AI 读',
  covered_to_seq  BIGINT UNSIGNED NOT NULL COMMENT '这条摘要覆盖到第几条消息',
  active          TINYINT(1)   NOT NULL DEFAULT 0,
  created_at      DATETIME(6)  NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
```

三个开关（默认值都跟老客户端一致）：`generate`（存完是否出话）、`immersive`（沉浸式，默认开）、`think`（上游思考，默认关）。

**上游挂了的语义**：用户消息**已经提交**，接口回 502 `upstream_error`，`details.seq` 告诉你它存到第几条。
客户端拿**同一个 `client_msg_id`** 重发，会得到 `duplicate:true / reply:null` —— 说明"话在、回复没出来"，不会重复存。

### 6.1 三个关键样例

**注册设备**

```http

200
{ "device_id": "9f3c...e1", "token": "b7d2...(64 hex)", "expires_at": null }
```

**写消息（幂等）**


## 7. 六条实现硬规矩（写代码时逐条对）

**7.1 时间一律 UTC。** 连接串里 `init_command="SET time_zone = '+00:00'"`，模型全用 `DATETIME(6)` 存 UTC；出参在序列化时转 ISO8601 带 `+00:00`。**不许在业务代码里 `datetime.now()`**，只用 `utcnow()` 一处封装。

**7.2 对外只给 `public_id`。** 自增 id 只在内网/日志里出现；`/v1` 的路径参数一律是 32 位 hex。

**7.3 seq 只能锁行分配。** 不许 `MAX(seq)+1`（并发必撞）。做法：
```python
# 先 SELECT ... FOR UPDATE 把会话行锁住，再 next_seq += 1，同一事务里插消息
conversation = repo.lock_conversation(db, conv_id)   # SELECT ... FOR UPDATE
seq = conversation.next_seq + 1
```

**7.4 幂等靠"锁行 + 预检"，唯一键是最后一道保险。** 具体做法（也是实际实现）：

1. `SELECT ... FOR UPDATE` 锁住会话行 → 同一会话的并发写在这里排队
2. 拿锁之后先查 `(conversation_id, client_msg_id)` 有没有 → 有就直接回 `duplicate: true`（200）
3. 没有才插入

为什么不用"先插、撞了就捕获异常"：那套写法要解析数据库报错字符串来判断"撞的是哪个唯一键"，
在 MySQL 的报错里翻字符串，读代码的人很难确认写对了没有。
锁行之后串行化，预检就是准的 —— 而唯一键仍然在，万一锁失效（bug）也不会写重复数据。

**7.5 异步路由 + 短事务。** 出话的路由是 `async def`，因为全链路唯一真正的等待是上游调用（几秒到几十秒），
那个等待必须 `await`，不能拿线程去堵。但同一函数里的数据库调用是**同步**的 —— 这是有意的取舍：

* 数据库操作必须是"单查询、走索引、毫秒级"，这种短阻塞对 2.4 请求/分钟的负载没有影响；
* 把每个 DB 调用都包进 `anyio.to_thread` 会让代码多出一层噪音，而收益接近 0；
* **绝对不许**在 async 路由里做慢查询（全表扫、大 JOIN）—— 那才是真正会卡死事件循环的东西。

另外两条边界：
* 生成期间**不持会话行锁**（先提交用户消息再出话），否则同一会话会被锁几十秒；
* SSE 流开始前把数据库连接还掉，流结束时用**新会话**落库（见 §6 的流式说明）。

**7.6 每个请求一个 `request_id`。** 中间件生成，写进日志、错误体、`usage_events`。排障时一条 id 串起全链路。
（实现上由 `main.py` 的中间件塞进 `request.state`，出话时作为 `usage_events.request_id` 落库。）

**7.7 提示词结构（实际实现，2026-11-15 20:3x 定稿）**

```
[system] 安全协议        config.safety_protocol，热改、60 秒缓存
[system] 世界观          config.worldview
[system] 角色 + 风格规则  character_prompts（active=1）+ EMPHASIS_RULE
[system] 前情提要        conversations.summary_head（每次压缩换掉）
[system] 永久记忆        conversations.memory（摘要再压一次，5~9 条，≤1200 字）
 …历史（按预算从最新往回装，已被摘要覆盖的不再发原文）…
[system] 检索片段        仅本轮，插在最后一条 user 之前
[user]   本轮输入
```

**两层记忆的分工**（这是"聊几百轮还记得开头"的关键）：

| 层 | 来源 | 体量 | 变化频率 |
|---|---|---|---|
| 前情提要 | 被挤出去的那段历史压成"情节纪要" | 800–1500 字 | 每次压缩换掉 |
| 永久记忆 | 旧永久记忆 + 新提要，**再压一次** | 5–9 条、≤1200 字 | 只增不减地被提纯 |

为什么要第二次压缩：摘要会越滚越长，几轮之后它就变成第二份历史；
永久记忆必须**恒定地小**，否则"记得开头"这件事本身会开始吃预算。

三处设计依据（不是拍脑袋）：

1. **安全协议独立成段**，排最前。它和人设的改动频率、优先级都不同；混进角色提示词里，
   改规则就得改所有人设。
2. **检索片段插在最后一条 user 之前**，不跟前面三段排一起。两个理由：
   缓存（它每轮都变，放前面会把历史全顶掉）；注意力（紧贴问题的内容权重最高）。
3. **固定前缀永不裁**，预算只裁历史（见 `app/prompt/budget.py`）。

风格规则整段照抄老后端 `rules.py`，沉默式（沉浸式）时整段替换而不是追加 —— 这两条都有测试守着。

### 8.1 为什么不用 WSL 里的 MySQL（实测，别再来一遍）

数据目录放在 `/mnt/d`（Windows 盘走 9p）时：

```
[ERROR] Can't start server : Bind on unix socket: Operation not supported
```

MySQL 在 Linux 上**必须**建一个 Unix socket，而 9p 挂载不支持建 socket；socket 又只能放在 Linux 原生盘 —— 那就必然把文件落到 `BakerAI_new` 外面，与 §0 冲突。所以改用 Windows 便携版：

- 没有 socket 问题，TCP 直连 `127.0.0.1:3307`
- I/O 走本地 NTFS，比 9p 快得多
- 不会因为 WSL 空闲休眠而停（老坑：`vmIdleTimeout`）
- 代价：248 MB 安装包 + 约 1 GB 解压，一次性

### 8.2 便携版带来的一条新纪律

Windows 的 MySQL 默认 `lower_case_table_names=1`（表名大小写不敏感），Linux 服务器默认是 `0`（敏感）。为了让两边行为一致：

> **库名、表名、列名、索引名、约束名，一律全小写 + 下划线。** 不许出现 `UserLog`。

这条已写进 §4 第 1 条（命名规矩），review 时一起看。

### 8.3 实测下来的四个坑（都写进脚本注释了，别再踩）

| 坑 | 现象 | 根因 |
|---|---|---|
| `mysqladmin ping` 判断存活 | 明明没起来，脚本说"已经在跑了"；或者连到了**别的实例**上 | ping 只要服务器回了话就返回 0，**密码错也算活**。改成真跑一句 `SELECT 1` |
| 客户端连到了 3306 | 报 `ERROR 1698 (28000) Access denied for user 'root'@'localhost'` | my.ini 只写了 `[mysqld]`，`mysql.exe` 不知道端口，用默认 3306 —— 那是 CloverWebChat 的库。必须补 `[client]` 段 |
| `skip-name-resolve` | 报 `ERROR 1130 Host '127.0.0.1' is not allowed` | 加了这参数后 127.0.0.1 不再反解成 `localhost`，初始化建的 `root@localhost` 匹配不上 |
| 脚本"卡住不返回" | `dev_mysql.ps1 start` 一直不结束，但库里其实已经起来了 | mysqld 继承了调用方的 stdout 管道，调用方等管道关闭。用 `-WindowStyle Hidden` 给它独立控制台 |
