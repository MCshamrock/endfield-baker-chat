# 输入推荐（"接下来我可以说什么"）

> 2026-11-17。老客户端等的就是 `POST /chat/suggestions` 这个端点；新客户端走 `/v1`。
> 三个入口（老单聊 / 老群聊 / 新客户端）**共用同一段提示词和同一个解析器**。

## 1. 端点

| 入口 | 端点 | 谁在用 |
|---|---|---|
| 老客户端单聊 | `POST /chat/suggestions` | 现网 EXE/APK |
| 老客户端群聊 | `POST /group/suggestions` | 现网群聊 |
| 新客户端 | `POST /v1/conversations/{id}/suggestions` | 新版 |

统一响应：

```json
{"suggestions": ["嗯，然后呢？", "所以你到底想说什么", "算了，先不说这个"]}
```

老协议只认 `{"suggestions": [...]}`；新接口多一个 `SuggestionsOut` 包装，字段名一致。

## 2. 三条硬规矩

### 2.1 失败返回空列表，不报错

推荐是锦上添花。上游挂了、解析失败、模型抽风 —— **一律 `[]` + 200**。
让聊天界面因为一个辅助功能弹错误框，是最典型的"小功能搞坏主流程"。
（测试 `test_legacy_suggestions_swallow_upstream_failure` 守着这条。）

### 2.2 只生成"玩家会打出去的话"

第一人称、≤25 字、口语、三条要有差异（顺着聊 / 换个角度 / 抛新引子）。
这是老后端的口径，没改 —— 推荐写成旁白或角色的台词，玩家一眼就知道是假的。

### 2.3 客户端必须"点开面板才拉"

每次推荐 = 一次真实上游调用。每轮都拉的话：

- 一次聊天从 1 次调用变 2 次，**限速提前撞满**；
- 表现是"聊一会儿自己停了"，而日志里看不出是推荐把额度吃掉的。

老后端就是被这个逼成按需的（`want_suggestions` 默认 true 但前端现在传 false）。

## 3. 实现落点

| 文件 | 职责 |
|---|---|
| `app/prompt/suggest.py` | 提示词 + 材料拼装 + JSON 解析（纯函数，可单测） |
| `app/suggestions.py` | 业务：取历史、调上游、失败兜底 |
| `app/api/legacy.py` | `/chat/suggestions` |
| `app/api/legacy_group.py` | `/group/suggestions`（改用共用模块，删掉了自己那份提示词副本） |
| `app/api/conversations.py` | `/v1/conversations/{id}/suggestions` |

**去重的原因**：三个入口各写一份提示词，改一处忘两处是必然的。
现在群聊那份也删了，只有 `app/prompt/suggest.py` 一处。

## 4. 不记账、不落库

- **不记 `usage_events`**：它会污染"每轮花了多少 token"的统计，而推荐的量很小；
- **不写消息表**：推荐是临时的，玩家不选就消失了。

## 5. 边界

| 情况 | 行为 |
|---|---|
| 会话还没有任何消息 | 照样能生成（材料里写"（还没有对话）"） |
| 别人的会话 | `/v1` 返回 404（按归属鉴权） |
| 群聊旁观模式 | 空列表（老需求：旁观不参与对话） |
| 上游 429 | 空列表 + 日志 warning（和挂掉一样处理） |
