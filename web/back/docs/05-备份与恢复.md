# 备份 BakerAI：一条命令，跑完自检

> 2026-11-16 立。起因很简单：这个项目上线前**一份备份都没有**，库里 36 个角色、
> 147 条世界书、47 把 key 和用户聊过的内容全在一块盘上。

## 0. 一句话

```powershell
.venv\Scripts\python.exe scripts\backup.py            # 备份 + 自检
.venv\Scripts\python.exe scripts\backup.py --verify   # 再真恢复一遍验行数
```

产物在 `_runtime/backups/baker-YYYYMMDD-HHMMSS/`（`_runtime/` 已在 `.gitignore` 里）。

## 1. 包里有什么

| 文件 | 内容 | 说明 |
|---|---|---|
| `db.sql.gz` | 整库 dump | `mysqldump --single-transaction`，导出期间不锁表 |
| `uploads.tar.gz` | 用户上传的图片 | 没有图片就不生成 |
| `.env` | 配置（含 `BAKER_SECRET`） | **没有它，`api_keys` 里的 key 一个都解不开** |
| `manifest.json` | 清单 | 每张表行数、每个文件的 sha256、mysqldump 路径与时间 |

## 2. 三条设计规矩（也都是踩过的坑）

1. **先写临时目录，校验通过再改名**。备份跑一半断掉，不会留下一个"看着像备份"的坏包。
2. **跑完立刻回读**：文件在不在、大小对不对、sha256 对不对、gzip 能不能解。
   没验过的备份不算备份。
3. **默认保留 14 份**，超了删最旧的。备份把磁盘塞满也是事故。

## 3. 恢复（出事时照这个做）

```bash
# ① 解压
tar -xzf baker-20261116-234200/uploads.tar.gz -C /path/to/_runtime/
gunzip -c baker-20261116-234200/db.sql.gz > /tmp/baker.sql

# ② 建空库（账号要有建库权限）
mysql -h127.0.0.1 -P3306 -uroot -p -e "CREATE DATABASE baker_back CHARACTER SET utf8mb4"

# ③ 导入（一定要指定字符集，否则中文会按客户端默认编码解释，乱码且不报错）
mysql -h127.0.0.1 -P3306 -uroot -p --default-character-set=utf8mb4 baker_back < /tmp/baker.sql

# ④ 核对行数：跟 manifest.json 里的 tables 逐个比
python - <<'PY'
import json; print(json.load(open("baker-20261116-234200/manifest.json"))["tables"])
PY

# ⑤ 把 .env 放回 web/back/.env（BAKER_SECRET 必须与备份时一致）
```

## 4. 一次性准备：验证用的临时库

`--verify` 会真把 dump 导入一个临时库再比行数，这是"备份能不能用"的唯一证明。
业务账号通常没有建库权限，所以本地建一次它：

```sql
CREATE DATABASE IF NOT EXISTS baker_back_verify CHARACTER SET utf8mb4;
GRANT ALL PRIVILEGES ON `baker\_back\_verify`.* TO 'baker'@'%';
FLUSH PRIVILEGES;
```

没这个库也不会报错 —— 脚本会照常备份，只是跳过恢复校验。

## 5. 定时

### Ubuntu（生产建议）

```cron
# 每天 03:30 备份，保留 14 份
30 3 * * * cd /opt/baker/back && .venv/bin/python scripts/backup.py --keep 14 >> ../_runtime/backups/cron.log 2>&1
# 每周日 04:10 多做一次"真恢复校验"
10 4 * * 0 cd /opt/baker/back && .venv/bin/python scripts/backup.py --keep 14 --verify >> ../_runtime/backups/cron.log 2>&1
```

### Windows（开发机）

```powershell
schtasks /Create /TN "BakerAI 每日备份" /SC DAILY /ST 03:30 ^
  /TR "pwsh -File \"F:\dshworkspace\BakerAI\BakerAI_new\web\back\scripts\backup.ps1\""
```

`scripts/backup.ps1` 只是切到后端口目录再调 python，没有别的逻辑。

## 6. 已知边界（别指望它兜这些）

| 不兜 | 原因 | 怎么办 |
|---|---|---|
| 硬盘整个坏掉 | 备份和数据在同一块盘上 | 定期把 `_runtime/backups` 同步到别的机器/网盘（`rsync -a` 或网盘客户端） |
| 备份期间正在写的图片 | 库是事务快照，图片目录是"打包那一刻"的照片 | 两次备份之间差的图片不会丢（下次还打包），但**可能与库不完全对齐**单张 |
| 误删数据后立刻发现 | 默认保留 14 天，第 15 天才发现就没了 | 出事别急着跑新的备份覆盖；先把出问题的备份另存一份 |
| `BAKER_SECRET` 丢了 | dump 里的 key 是密文 | `.env` 在包里，**把包当机密文件对待**；不要把包传到公开网盘 |

## 7. 验收记录（2026-11-16 首次跑通）

```
库：313 行 / 20 张表，dump 287 KB
图片：8 个文件，1 KB
回读校验：文件齐全、sha256 与 gzip 都通过
恢复校验：20 张表行数全部一致
产物：_runtime/backups/baker-20261116-234200（289 KB）
```

过程中踩到两个 Windows 特有的坑，都已经写进脚本注释：
- `subprocess` 的 `stdout`/`stdin` 塞 gzip 对象会**绕过压缩**（`GzipFile.fileno()` 指向压缩文件本身），
  得到的是"名字叫 .gz、内容是明文"的假备份 —— 只有回读校验能发现。
- `mkstemp` 返回的文件描述符没关，Windows 上紧接着 `unlink` 会报"文件被占用"。
