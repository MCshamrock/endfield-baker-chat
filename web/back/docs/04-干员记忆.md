# 干员记忆 · 项目书 v0.1

> 状态：草案，待拍板。2026-11-16。
> 对应工程：`BakerAI_new/web/back`（Python 3.14 + FastAPI + MySQL 8.4）。
> 一句话：**她记得你这个人，不管你在哪个对话里说过。**

---

## 0. 一页纸

| 项 | 决定 |
|---|---|
| 记什么 | 只记「人情账」：称呼、偏好、关系、约定、你的身份背景 |
| 不记什么 | 剧情不跨对话。上一局的故事留在那一局，不开新卷 |
| 挂在谁名下 | 「玩家 × 干员」一对。同一账号（或同一台访客设备）下所有对话共享 |
| 写 | **永远开，不给关**。关掉她连这一局都不记得，那不是用户要的「干净」 |
| 读 | 可关。全局一个默认值，单独一个对话可以覆盖 |
| 冲突 | 按时间取新；单值类型新写自动覆盖旧的 |
| 删除 | 软删 + 留指纹。删掉的**不会被下一次提炼复活** |
| 首句 | 新对话第一条回复必须主动用上账本，否则用户感知不到这个功能存在 |
| 体量 | 单条 ≤40 字；每个干员上限 40 条；注入上限 24 条 / 600 字 |

## 1. 为什么只做「人情账」

群聊里有人问「跨对话记忆是什么」，最直觉的回答是「A 对话里让他记住一件事，B 对话里他也知道」。这句话里其实混了两样东西：

- A 里你说「我叫阿哲」——这是**关于你的事实**，它跨对话成立，而且本该成立。
- A 里你们在雪山打了一场——这是**一段故事**，它跨对话不成立。用户在 B 里开新局，本来就是想换一局。

把两样都做成「跨对话共享」，第二样会立刻出事：B 里她突然提起 A 的甜言蜜语、B 里她还记着 A 的仇、A 说喜欢猫 B 说讨厌猫。这类 bug 说两句测不出来，要聊很久才暴露，而且一暴露就是人设崩塌级别的投诉。

**所以 v1 只做第一样。** 剧情账继续留在会话内（现有的「前情提要 + 永久记忆」就是它，不用动）。这样：

- 用户要的「她记得我」成立；
- 用户要的「开个干净的一局」天然成立——不是靠开关关掉什么，而是剧情本来就不跨；
- 开关只剩一个语义，好解释、好测、好做。

> 剧情账要跨对话，需要先引入「故事线」概念（哪几个对话属于同一卷）。那是下一期的事，见 §15。

## 2. 心智模型

**对玩家**：每个干员有一本小本子，只记「你和这个干员之间的事」。你换了对话，本子跟着走。

**对模型**：一段固定格式的 system 文本，常驻，不靠检索。

两类知识的分界，一句话能说清：

| | 例子 | 归属 | 跨对话 |
|---|---|---|---|
| **人情账**（bond） | 你的名字、你怕黑、她叫你「笨蛋」、你答应带她看雪 | 玩家 × 干员 | **是** |
| **剧情账** | 你们在雪山打过一场、谁欠谁一条命、那个伏笔还没收 | 单个对话 | 否 |

---

## 3. 规则

### 3.1 开关只有两层

| 层级 | 存哪 | 语义 |
|---|---|---|
| 全局默认 | 一个玩家一行 | 我这个人，默认让干员记住我 |
| 单对话覆盖 | 建对话时选，之后可改 | 这一局，换个干净的 |

**不做第三层**（每个干员单独开关）。玩家脑子里「她」是同一个，分到角色级只会让人困惑。

### 3.2 默认值

**默认开。**

理由：默认关的话绝大多数人不会去开，功能等于没做；而默认开能立刻兑现「她真的记得我」这个惊喜。

老用户「我开新对话就是想重来」的诉求，用**新建对话时的一句轻提示**解决，不用弹窗：

> 她会记得你之前说过的话 · [换个干净的]

点一下就把这一局的读取关掉。成本远低于默认关 + 引导开。

### 3.3 什么不记

这些即使模型提炼出来了也要丢掉：

- 剧情过程（谁打了谁、去了哪、发生了什么）—— 属于会话内
- 对第三人的评价（群里其他人说了什么）
- 情绪化的气话（「我恨你」）—— 一小时后就反悔的东西不该进永久账
- 任何含完整联系方式、地址、真实姓名的内容（除非玩家主动要求记住）

## 4. 写入

### 4.1 三个触发点

| 时机 | 成本 | 说明 |
|---|---|---|
| **压缩时**（主路径） | 0 额外调用 | 现有压缩流程已经产出结构化摘要，顺手分拣出人情账即可 |
| **对话收尾**（兜底） | 一次小调用 | 只在「这个对话从没压缩过」时跑，防止短对话什么都不写 |
| **玩家手动**（v1 不做） | — | 留接口，见 §15 |

压缩是「上下文长了才发生」的，所以必须有兜底，否则新用户聊了三句就换对话，账本还是空的。

### 4.2 提炼的输入输出

输入：

```
已有账本（active 条目，带 id）
本对话的新增摘要（结构化：memory / plot / state / timeline）
```

输出（严格 JSON）：

```json
{
  "add": [
    {"kind": "nickname", "text": "你叫阿哲", "confidence": 3}
  ],
  "supersede": [
    {"id": 42, "by": "你其实叫老陈"}
  ]
}
```

`supersede` 是这套设计里最关键的一个字段：**让模型在写入的同时指出哪条旧记忆被推翻了**。它本来就要看已有条目（现有永久记忆的提炼逻辑就是这样），多要一个字段是零成本的，但换来的是「她不会同时相信两个矛盾的设定」。

### 4.3 条目的形状：固定 8 类

kind 是**封闭枚举**，写死在代码里，模型只能选，不能自造。新增一类要发版。

| kind | 基数 | 例子 |
|---|---|---|
| `nickname` | 单 | 你叫阿哲 |
| `call` | 单 | 她叫你「阿哲」，生气时叫「笨蛋」 |
| `appearance` | 单 | 你左眉有道疤（玩家自己说的） |
| `relation` | 单 | 你们现在是搭档 |
| `preference` | 多 | 你怕黑 / 你爱喝冰美式 |
| `dislike` | 多 | 你受不了香菜 |
| `promise` | 多 | 你答应过带她看雪 |
| `fact` | 多 | 你是罗德岛的博士 |

**单值**（同一玩家 × 同一干员只留一条）：新的覆盖旧的，旧的自动标 `superseded`。
**多值**：可以并存；只有模型显式判为矛盾时才走 `supersede`。

这条「基数」规则是整个一致性的地基。没有它，`nickname` 会出现三条，模型看到三个名字，要么随机挑一个，要么和稀泥。

### 4.4 去重

每条写入前算指纹：

```
fingerprint = sha256(owner_key + "|" + character_id + "|" + kind + "|" + 归一化(text))[:16]
```

归一化 = 去首尾空白 + 去所有标点空白。指纹相同即为同一条，跳过。

唯一键 `(owner_key, character_id, fingerprint)` 让并发写入也不会重复。

### 4.5 容量

- 单条 `text` ≤ 40 字（超过就说明这条混了两件事，退回让模型拆）
- 每个干员的 active 条目上限 **40 条**
- 写入时若超上限：把 `last_used_at` 最旧、且 `pinned = 0` 的一条标 superseded，腾位子

不做时间衰减。「你答应下周带她看雪」这种过期语义，v1 靠用户手动删或新条目覆盖，**明确写在文档里，避免以后被当 bug 报**。

## 5. 读取与注入

### 5.1 注入位置

现有 prompt 层次：

```
安全协议 → 世界观 → 世界书索引 → 常驻 → 角色+风格规则 → 前情提要 → 永久记忆 → 历史 → 检索正文 → 本轮
```

人情账插在**角色+风格规则之后、前情提要之前**：

```
… → 角色+风格规则 → 【她记得关于你的事】 → 前情提要 → 永久记忆 → …
```

理由：它是「她对这个人的认知」，属于人设的延伸，不该等到剧情讲完才出现。

### 5.2 注入格式

```
【她记得关于你的事】
· 你叫阿哲；她平时叫你「阿哲」，生气时叫「笨蛋」
· 你怕黑，睡前要开着小灯
· 你答应过下次带她去看雪
```

要求：

- 按 kind 分组、按 `updated_at` 倒序，最多 24 条 / 600 字
- 只有 `active` 的进
- 玩家关了这一局的读取 → 整块不出现（但写入照常，见 §3.1）

### 5.3 首句规则

在「角色+风格规则」里加一条硬规则：

> 若【她记得关于你的事】里有能自然带出的内容，**本轮第一句必须用上**（叫出称呼、提到对方的偏好或约定），不要生硬罗列，也不要每句都提。

**这条不写，功能做了等于白做。** 用户判断「她记不记得我」只看她有没有主动提——不主动提 = 没记。

### 5.4 群聊

| 场景 | 写 | 读 |
|---|---|---|
| 群里随便聊 | 不写人情账 | 按开关读取 |
| 群里被 @ 并直接对话 | **写**（这段是「她和你」的） | 读 |
| 单聊 | 写 | 读 |

理由：群聊里有一屋子人，她说的话未必是对你说的。不加 @ 就不写，避免单聊账本被群聊污染。

## 6. 冲突

| 情况 | 处理 |
|---|---|
| 单值 kind 再出现 | 新覆盖旧，旧条 `superseded` |
| 多值 kind 但模型判为矛盾 | 模型在 `supersede` 里指定，旧条失效 |
| 两条都对（早上的我和晚上的我） | 并存，注入时按时间倒序，模型自然按最近的说话 |
| 来源不同的同一条 | 指纹相同 → 去重，保留 `updated_at` 新的 |

**不允许**「两条都留着让模型自己选」—— 那是所有记忆类功能里最典型的翻车方式。

---

## 7. 删除

用户删一条 → `status = 'deleted'`，**不物理删，指纹留档**。

写入时检查：指纹已存在且 `status = 'deleted'` → 跳过，不再写回。

这一步看着多余，实际是两个功能的地基：

- 「用户让我忘掉」必须真的忘掉，否则下次提炼又冒出来，用户会觉得被骗；
- 「记忆面板」敢把全部条目摊开给用户看，靠的就是删了不会复活。

另外：删除要连带把「同指纹的其他条目」一起删（同账号多设备时可能存在两份）。

## 8. 登录与多设备

沿用现有归属体系（`user_id` 优先，否则 `device_id`），不新增身份概念。

| 事件 | 动作 |
|---|---|
| 访客登录 | 该设备名下所有记忆的 `owner_key` 从 `d:456` 改写成 `u:123`；同指纹冲突跳过 |
| 同一账号第二台设备 | 各设备记忆取并集，指纹去重 |
| 登出 | 记忆跟着账号走，留在账号名下（和会话的规则一致） |
| 同一设备换账号 | 已有 409 拦截，记忆自然隔离 |

`owner_key` 格式固定：`u:<user_id>` / `d:<device_id>`，最长 32 字符。

## 9. 数据模型

### 9.1 新表 `character_memories`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `owner_key` | VARCHAR(32) | `u:123` / `d:456` |
| `character_id` | BIGINT UNSIGNED | 哪个干员 |
| `kind` | VARCHAR(16) | §4.3 的 8 类之一 |
| `text` | VARCHAR(300) | 一条一件事，≤40 字 |
| `fingerprint` | CHAR(16) | §4.4 |
| `status` | ENUM('active','superseded','deleted') | |
| `supersedes_id` | BIGINT UNSIGNED NULL | 被它推翻的那条 |
| `source_conversation_id` | BIGINT UNSIGNED NULL | 哪来的（便于"看上下文"） |
| `pinned` | TINYINT(1) | 用户置顶，永不被容量淘汰 |
| `created_at` | DATETIME(6) | |
| `updated_at` | DATETIME(6) | |
| `last_used_at` | DATETIME(6) | 上次被注入的时间（淘汰依据） |

索引：

```
UNIQUE uk_mem_owner_char_fp (owner_key, character_id, fingerprint)
KEY ix_mem_lookup (owner_key, character_id, status, kind)
KEY ix_mem_char_status (character_id, status)
```

### 9.2 新表 `memory_settings`

| 字段 | 类型 |
|---|---|
| `owner_key` | VARCHAR(32) PK |
| `mode` | ENUM('on','off') DEFAULT 'on' |
| `updated_at` | DATETIME(6) |

没有行 = 默认 on。单独建小表，不动 `devices` / `users`。

### 9.3 改 `conversations`

```sql
ALTER TABLE conversations
  ADD COLUMN memory_mode ENUM('inherit','on','off') NOT NULL DEFAULT 'inherit';
```

`inherit` = 跟随全局。

## 11. 老数据迁移

**不做。**

现有的 `conversations.memory` 是剧情账文本（「她记得你抢了她的面包」这类），从里面抽「人情账」的准确率很低，抽出来的多是噪音。强行迁移的收益是 0，风险是给老用户塞一屏错的记忆。

v1 从空账本开始，用户第一次聊天就建立。没有感知损失——以前本来就没有这个功能。

## 12. 成本

| 项 | 量 |
|---|---|
| 常驻注入 | 最多 24 条 / 600 字 ≈ 900 token（实际多数账号只有 5~15 条） |
| 压缩时分拣 | 0 额外调用（复用现有压缩调用，只改输出 schema） |
| 兜底提炼 | 每个对话一次，输入 ~900 / 输出 ~400 token |
| 表体积 | 单账号 × 36 干员 × 40 条 × ~300 B ≈ 430 KB |

结论：现有 prompt 固定前缀约 6.5k token（索引瘦身后）；加人情账后仍在 7.5k 上下，
占 20 万预算的 4%。可以忽略。

> 上下文预算 2026-11-16 起是 **20 万 token、超预算只压缩不裁切**（见 `01-工程进度总览.md` §2.1）。
> 人情账进的是"固定前缀"，所以它永远在场，不会被压缩掉 —— 这正是它和剧情账的分工。

## 13. 验收

这些必须能跑出来，跑不出来就是没做完：

1. A 对话说「我叫阿哲」→ 开 B 对话，她**第一句**就叫出阿哲
2. 关掉读取 → B 对话不知道，A 对话仍然知道（只影响一局）
3. 改口「其实我叫老陈」→ A 里旧条目变 `superseded`，B 里叫老陈，不会同时出现两个名字
4. 删掉一条 → 列表里没了，再聊十轮也不会复活
5. 群聊里 @ 她 → 说得出的名字；不 @ 时不自作主张提
6. 访客登录 → 设备名下记忆跟着账号走
7. 注入增量 < 900 token（对比开/关同一对话的 prompt token）
8. 并发写入同一干员 → 唯一键挡住，不出现重复条目

## 15. 明确不做

| 不做 | 原因 |
|---|---|
| 剧情跨对话 | 需要「故事线」概念，且串味风险高。下一期单独做 |
| 每个干员单独开关 | 心智负担大于收益 |
| 向量 / embedding 检索 | 人情账条目少，全量注入就够；等条目过百再说 |
| 时间衰减、自动遗忘 | 语义判断不可靠，会误删用户在意的东西 |
| 干员之间共享记忆 | A 干员知道你告诉 B 的事——最容易崩人设的一条，明确禁止 |
| 老数据迁移 | 见 §11 |
| 玩家手写记忆 | 留接口，v1 不做；先看用户想不想自己写 |

---

## 16. 风险

| 风险 | 应对 |
|---|---|
| 模型提炼出垃圾条目 | kind 封闭 + 40 字上限 + 面板可见可删 |
| 「她提得太频繁」 | 规则里写「不要每句都提」，注入时按 `last_used_at` 降权：1 小时内提过的条本次排在后面 |
| 删了又复活 | §7 的指纹留档，测试用例 4 守住 |
| 多设备两份不一致 | 指纹唯一键 + 按时间取新 |
| 群聊污染单聊 | §5.4，不加 @ 不写 |

**与 §4.2 的差异（如实记下）**：提炼没有复用压缩那一次调用，而是**单独一次小调用**
（输入 ~900 / 输出 ≤600 token）。原因是两种输出的形状差太远（提要是长文本、账本是 `kind|内容` 行），
硬塞进一次调用会让两边都变差。成本上每次压缩多一次小调用，可接受。

**尚未做的一处取舍**：多值 kind（如 preference）的真冲突，v1 靠 `add` 时的指纹去重 +
让模型看着已有条目别重复写，不做"语义比对自动覆盖"。宁可并存两条，也不误删用户在意的东西。
