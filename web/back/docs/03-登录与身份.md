# 登录与身份（访客 / 账号）

> 2026-11-15 · 对应代码：`app/api/auth.py`、`app/passwords.py`、`app/repos/users.py`、`app/deps.py`
> 决策依据：`后端架构.md` §3「登录 + 访客：双轨，但数据归属必须一句话说死」

---

## 1. 三种状态，一句话分清

| 状态 | 手里有什么 | 数据归谁 | 能看见什么 |
|---|---|---|---|
| **访客**（默认） | 设备 token（匿名） | 这台设备（`device_id`，且 `user_id IS NULL`） | 只有这台设备的记录 |
| **已登录** | 设备 token（同一张，没换） | 账号（`conversations.user_id`） | **这个账号名下所有设备**的记录 |
| 老客户端 | 什么都没有 | 不落库（兼容层无状态） | 它自己的本地历史 |

关键：**登录不换 token**。客户端手里那张设备 token 继续用，登录只是给设备挂了一个
`owner_user_id`。好处是客户端只有一套凭证、没有"登录后要重新初始化"这一步；
坏处是 token 丢了等于设备丢了 —— 但用同一账号在新设备登录一次就能看回来。

## 2. 数据归属：只改一列

登录时做的事（`conversations_repo.adopt_owned`）只有一句：

```sql
UPDATE conversations SET user_id = :uid
WHERE device_id = :did AND user_id IS NULL
```

为什么这样就够了：

* 登录**前**在设备上聊的 → `user_id` 空着，登录时补上，从此属于账号；
* 登录**后**新建的 → 建的时候就写 `user_id`；
* 同一账号的第二台设备 → 查的是 `WHERE user_id = :uid`，天然看得见；
* **不需要搬数据、不需要合并、不需要两份数据对账**。这是"服务器是唯一真相"的直接结果。

### 2.1 查询条件（`_owner_scope`）

```python
if user_id is not None:      # 已登录
    WHERE user_id = :uid
else:                        # 访客
    WHERE device_id = :did AND user_id IS NULL
```

访客那条为什么还要 `user_id IS NULL`：一台设备可能被前一个账号登录过、又登出了。
那些记录的 `user_id` 还指向前一个账号，**不能露给现在的访客**（共用手机的场景）。

### 2.2 登出不删数据

登出只是 `devices.owner_user_id = NULL`。记录本身一条没动，只是这台设备"看不见"了 ——
重新登录立刻回来。这是安全侧该有的行为：手机递给别人之前点一下登出，记录就藏起来了。

## 3. 接口

```
POST   /v1/auth/device     注册匿名设备（唯一不需要 token 的端点）
POST   /v1/auth/register   用户名 + 密码注册 → 当场登录，返回 {user, adopted_conversations}
POST   /v1/auth/login      用户名 + 密码登录 → 返回 {user, adopted_conversations}
POST   /v1/auth/logout     退出（设备留在原地，数据在账号里）
GET    /v1/auth/me         kind=guest|user + user + devices[]
POST   /v1/auth/password   改密码（要验旧密码）
```

* `adopted_conversations`：这次登录把多少条"登录前在这台设备上聊的"划到了账号名下。
  客户端可以据此给一句"已把 3 条记录并入账号"。
* `/v1/meta` 的 `caps` 加了 `login`，客户端按它决定要不要显示"登录"入口。

### 3.1 为什么是用户名 + 密码（不做邮箱）

* **没有发信能力**。邮箱的唯一用处是"发验证码 / 找回密码"，这两件事现在都做不了
  —— 让用户填一个收不到信的邮箱只是多一步，还会让人以为"以后能靠它找回密码"。
* **用户是玩家**。注册时为了一个账号去拼英文邮箱，没必要。
* 表结构里 `login_type / login_id` 本来就是多登录方式预留的，将来加邮箱 / QQ
  只是多一个 `login_type`，不用改表（`schema/014` 已经把 `username` 加进枚举了）。

### 3.2 用户名规则（前后端必须一致）

```
2–20 个字符；只能用 中文 / 字母 / 数字 / 下划线；首位必须是中文或字母
```

* **允许中文**：`三叶草`、`佩丽卡的狗` 都是合法用户名。让玩家为了注册去拼英文名不合理。
* **大小写不敏感**靠 MySQL 的 `utf8mb4_0900_ai_ci` 排序规则：`Clover` 和 `clover`
  落在同一个唯一键值上。所以代码里**不做 `lower()`**（那样会造出"库里存原样、
  查的时候小写"两套口径），存用户打的原样，比对交给库。
* 昵称（`display_name`）和用户名分开：用户名要唯一且字符集受限，昵称可以随便写
  （将来会进提示词，让人格叫得顺口）。不填就用用户名。

## 4. 密码怎么存

`app/passwords.py`，**只用标准库**（`hashlib.scrypt`）：

```
scrypt$16384$8$1$<salt base64>$<hash base64>
```

* 不引 bcrypt/argon2：依赖以 `requirements.lock` 为准，本机与服务器必须逐条一致，
  多一个编译型依赖就多一处"服务器上装不上"的风险。scrypt 是标准库、底层 OpenSSL，
  强度同档。
* `hashlib.scrypt` 不可用时自动降级 `pbkdf2_sha256`（60 万次），格式自带前缀区分，
  换算法不用改表。
* 三条细节都写在文件头了：**先 NFKC 归一化**（全角/半角密码在用户眼里一样）、
  **`hmac.compare_digest`**（不用 `==`，防时序攻击）、**每次新随机盐**。

### 4.1 登录失败为什么不区分"账号不存在"和"密码错"

分开说等于送了一个"这个用户名有人用没有"的探测接口。所以：

* 两种情况都回 `bad_credentials` / 401 / 同一句话；
* 账号不存在时**照样跑一遍真哈希**（`_DUMMY_HASH`），否则响应时间快一个数量级，
  用计时就能把注册过的用户名筛出来。

### 4.2 防爆破：两道闸门

| 闸门 | 额度 | 挡什么 |
|---|---|---|
| 每设备 | 10 次 / 分钟 | 拿一台机器狂试密码 |
| 每账号 | 20 次 / 15 分钟 | 换设备继续试同一个账号 |

两道是乘法关系：重装 App 能换一台设备（绕过第一道），但第二道还按账号拦着。
账号那道的 key 取**小写**（`Alice` 和 `alice` 是同一个账号，否则换个大小写就换了个桶）。
都是进程内固定窗口（单进程部署，重启清零），要精确限流得上 Redis —— 这个量级不值得。

**试对了就把该账号的失败计数清零**：否则白天误输两次、晚上再错一次，会被当成
"连续错三次"。清零只清账号那一道，设备那道不清（设备额度本来就够松）。

### 4.3 哈希闸门：和限流是两件事

限流管"一个人试几次"，`app/gates.py` 管"同一时刻有几个请求在算哈希"。

scrypt 一次要吃 16 MB 内存、几十毫秒 CPU，而登录接口**不需要登录**，谁都能打。
没有闸门时几百个并发请求会同时申请几百个 16 MB 缓冲 —— 进程不是被刷爆带宽，
是被自己的内存申请拖死。所以同时只放 **2 个**进来算，占不到位置立刻回 429
（不排队：排队只会把请求拖到超时，用户体验更差）。

**改密码时先把其它设备全摘掉**（`devices_repo.unbind_others`）。这是"改密后所有会话
失效"在本架构里的等价物：别人手里的旧手机立刻看不到这个账号的数据，自己这台不用
重新登录。设备本身和 token 都还在，只是从账号上摘下来 —— 数据一条没动。

## 5. 同一台设备换账号：必须拒绝

设备已经挂着 A 账号，直接登录 B 账号 → `409 device_taken`，要求先登出。

理由：设备上有 A 的记录（`device_id` 是这台设备）。如果悄悄把设备改挂到 B，
那些记录的 `user_id` 虽然还指向 A，但**附件**是按 `device_id` 判归属的 ——
B 会看到 A 上传的图。所以这里宁可多一次操作，也不留这个口子。

## 6. 前端要做的三件事

1. 启动时调 `GET /v1/auth/me`，`kind=guest` 显示"登录"，`kind=user` 显示昵称。
2. 登录/注册成功后**什么都别做** —— token 没变、会话不用重拉（列表本来就按账号查）。
   如果接口回了 `adopted_conversations > 0`，弹一句"已把 N 条记录并入账号"。
3. 登出后要清本地缓存并回到访客状态（服务端已经看不到那些记录了，本地不清会显示幽灵数据）。

## 7. 明确没做的

| 项 | 为什么现在不做 | 什么时候做 |
|---|---|---|
| 邮箱 / 手机号登录、验证码、找回密码 | 要 SMTP / 短信，服务器还没配 | 配好之后，照 CloverWebChat 那套抄一遍（`email_codes` 三用途 + 一次性 + 5 次作废） |
| 忘记密码 | 现在**只能管理员重置**（没有第二条验证身份的途径） | 有了发信能力之后 |
| 设备绑定码（输 8 位码直接换机） | **输密码已经能换机**，绑定码只是少输几个字 | 有人抱怨时再做 |
| 第三方登录（QQ/微信） | 要企业资质 | 不做 |
| 删号 / 数据导出 | 属于后台与合规，先有备份再说 | 后台那一刀 |
| 密码错误锁定（永久锁） | 现在只有速率限制，没有"错 5 次锁 15 分钟" | 如果真被爆破再加 |

## 9. 与 CloverWebChat 登录架构的对照

参考件：`CloverWebChat/docs/登录架构.md`（同一个人的另一个站）。两边都做完之后互相对照，
**相同的地方是验证过的经验，不同的地方是有理由的**。

### 9.1 完全一致的部分

| 项 | 两边做法 |
|---|---|
| 密码哈希 | `scrypt N=16384 r=8 p=1 keylen=64`，先 `NFKC` 归一化，16 字节随机盐，格式 `scrypt$N$r$p$saltB64$hashB64`，定时安全比较 |
| 时间抹平 | 账号不存在时**照样烧一次真哈希**，否则响应时间就是个"这个账号存在不存在"的探针 |
| 登录错误文案 | 不区分"没这个人"和"密码错"，同一个码、同一句话 |
| 双桶限流 | 按设备/IP + 按账号，两道是乘法关系 |
| 哈希闸门 | 同时最多 2 个 scrypt（见 §4.3） |
| 试对清计数 | 登录成功后把该账号的失败计数归零 |
| 改密清会话 | 那边删 `sessions` 行；这边摘设备（见 §4.3） |
| 库里只有哈希 | 密码只有 scrypt；token 只有 sha256；明文只在客户端 |

### 9.2 故意不同的部分

| 项 | CloverWebChat | BakerAI | 为什么 |
|---|---|---|---|
| 登录态载体 | **`sid` cookie（HttpOnly）+ `sessions` 表** | **设备 Bearer token**（同一张，不换） | 那边是网站，cookie 是自然选择；这边是 APK/EXE，先有设备身份、后有账号。登录换 token 会让"登录前聊的记录"多一次归属迁移，而改一列就够了 |
| 会话有效期 | 30 天，过期重新登录 | 设备 token **不过期** | 设备丢了/换了靠"新设备登录同一账号"救回来；给 App 加 30 天强制重登，掉的是所有访客用户，不只登录用户 |
| 找回密码 | 邮箱验证码（要 SMTP + Turnstile） | **暂无**，丢了只能管理员重置 | 没有发信能力。这一版先不做，做的时候照抄那边（`email_codes` 三用途 + 一次性 + 5 次作废） |
| 注册验证 | 邮箱验证码 + 可选邀请码 + 首个用户自动 admin | 用户名不验证、无邀请码、无 admin 概念 | 免费产品，注册门槛越低越好；后台管理是下一刀的事 |
| 密码强度 | ≥8 + 含大写 + 含小写 + 含数字 | **只要求 ≥8** | 强制复杂度最后只会让人把密码写在备忘录里。那边是因为有积分和付费，这边暂时没有 |
| 登录标识 | 用户名**或**邮箱（二选一填） | **只有用户名**（允许中文） | 那边邮箱用于找回密码；这边没有发信能力，邮箱没用处。将来要加邮箱登录，`login_type` 换一下就行 |

### 9.3 那边踩过、这边已经避开的坑

1. **时区差 8 小时**（`expires_at` 用 Node 时间写、用 MySQL `NOW()` 比）。
   这边全库 `DATETIME(6)` + 连接固定 `time_zone='+00:00'` + 只有一个 `utcnow()`，
   没有第二套时间来源。
2. **`ER_DUP_ENTRY` 冒 500**（两人同时抢注同一用户名）。这边注册是同进程单事务，
   撞唯一键会抛 `IntegrityError` —— 目前靠"先查再插"兜着；**并发极端情况下仍可能 500**，
   待办里记了一条（见 §7）。
3. **靠错误文案判断登录态**（前端搜"未登录"）。这边用 `GET /v1/auth/me` 的
   `kind=guest|user` 显式表达，不靠文案。
4. **cookie Domain 在 IP 下要回退**。这边没有 cookie，这类问题不存在；
   但反过来设备 token 一旦泄露就只能靠改密踢设备兜底（已实现）。
