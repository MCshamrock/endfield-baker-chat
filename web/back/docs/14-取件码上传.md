# 取件码上传

> 2026-11-18。新建的「先匿名传包、之后凭码领取」功能，外加给老客户端（3.2.0–3.2.2）的
> `/upload` `/fetch` 兼容层。代码：`app/api/uploads.py`（路由）、`app/uploads.py`（业务）、
> `app/repos/uploads.py`（表 + 盘）、`schema/018_upload_tickets.sql`、`scripts/cleanup_uploads.py`。

## 1. 为什么需要它

用户刚装好 APK、**还没有账号**，但手机里有一个几十兆的「导出数据包」想一起带过来。
原来的流程要么让他先注册、再回到设置里选一次文件（在最陌生的时刻干最麻烦的事），
要么数据就丢了。

拆成两步就顺了：

```
没登录：POST /v1/uploads  → 上传包 → 拿到 8 位取件码（AB3D7K9Q）
注册：  填这个码         → 同一个事务里把包导进新账号
```

码是给**人**用的，所以只有三条约束：8 位、全大写、字符集和线上老服务逐字一致 ——
`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（32 个字符，去掉 `0 O 1 I`，但**保留 L**）。
保留 L 不是偷懒：老客户端对码做格式校验（`^[A-HJ-NP-Z2-9]{8}$`），它认 L；
我们要是为了"更好抄"把 L 也去掉，生成的码里有 L 时会被老客户端判成"格式不对"。
32^8 ≈ 1.1×10^12 种，配合唯一索引，撞码可以当成不会发生。

## 2. 新接口（App 用）

### POST /v1/uploads —— 免登录上传

```http
POST /v1/uploads
Content-Type: multipart/form-data
file=<数据包 .json / .zip>
```

```json
201 Created
{
  "code": "AB3D7K9Q",
  "expires_at": "2026-11-19T00:31:07.512345+00:00",
  "bytes": 12345,
  "source": "json"
}
```

校验（都在上传这一步，**不做全量导入**）：

| 情况 | 结果 |
|---|---|
| 空文件 | 400 `bad_request` |
| 大于 `import_max_bytes`（默认 64MB） | 413 `too_large` |
| `imports/package.py` 认不出（不是 ZIP 也不是导出 JSON） | 400 `bad_package` |
| 全站取件区已满 2GB | 507 `storage_full`（提示里写了怎么清） |
| 同一 IP 一小时内超过 5 个 | 429 `too_many_uploads` |

落盘位置：`<upload_dir>/tickets/<code>.bin`。目录默认是
`BakerAI_new/_runtime/uploads/tickets/`（和附件同一个根，子目录分开）。

### GET /v1/uploads/{code} —— 只看码对不对

```json
200 OK
{
  "code": "AB3D7K9Q",
  "bytes": 12345,
  "source": "json",
  "expires_at": "2026-11-19T00:31:07.512345+00:00",
  "claimed": true,
  "claim_count": 2
}
```

**不回内容**。前端用它做"先确认码再注册"，比注册完才发现抄错码体验好。
`claimed` 只是"有没有人领过"（`claim_count > 0`），**不代表不能再领**。
不存在 → 404 `no_claim_code`；过期 → 400 `claim_code_expired`。

### POST /v1/uploads/claim —— 登录后领取

```http
POST /v1/uploads/claim
Authorization: Bearer <设备 token>
Content-Type: application/json

{"code": "ab3d7k9q"}        ← 小写/空格都行，服务端会归一化
```

返回**和 `POST /v1/imports` 完全一样**的形状（含 `duplicate`）：

```json
200 OK
{
  "id": "9f2c…", "duplicate": false, "source": "json", "mode": "merge",
  "package_version": 1, "cards": 1, "conversations": 1, "messages": 23,
  "images": 2, "skipped": 0, "notes": [], "created_at": "…", "revoked_at": null
}
```

要求登录（访客 401 `no_user`）：导入要挂在某个人名下，免登录领等于数据落在
匿名设备上、换台手机就找不回来。

### POST /v1/auth/register 新增可选字段

```json
{
  "username": "三叶草",
  "password": "……",
  "display_name": "三叶草",
  "claim_code": "AB3D7K9Q"
}
```

注册 + 绑设备 + 领取导入 **在同一个事务里**：码无效/过期 → 400 `bad_claim_code`，
整个注册回滚（不会出现"账号建好了数据没进来"）。成功时响应多一个
`import_result`（形状同上，没带码时是 `null`）：

```json
201 Created
{
  "user": {"id": "…", "username": "三叶草", "display_name": "三叶草", "created_at": "…"},
  "adopted_conversations": 0,
  "import_result": {"id": "…", "duplicate": false, "conversations": 1, "messages": 23, "…": "…"}
}
```

## 3. 码的语义：**不是一次性**

24 小时（`upload_ttl_hours`）内，同一个码可以被**多台设备、多个账号**分别领取：

| 谁领 | 结果 |
|---|---|
| 第一次（设备 A / 账号甲） | 导入，`duplicate=false` |
| 同一台设备再领 | 200，`duplicate=true`（导入管线按 `(设备, sha256)` 幂等），数据不多一份 |
| 换设备 B / 账号乙再领 | 200，`duplicate=false`，**各自独立一份**（落在自己账号下） |
| 过期后再领 | 400 `claim_code_expired` |

可领条件只有「没过期」。这是产品口径：码是"取件凭证"，不是"一次性优惠券"。

## 4. 领取的原子性

`repos/uploads.py: mark_claimed` 是一条 UPDATE：

```sql
UPDATE upload_tickets
   SET last_claimed_at = NOW(),
       claim_count     = claim_count + 1,
       claimed_device_id = ?, claimed_user_id = ?
 WHERE code = ? AND expires_at > NOW()
```

看 `rowcount`：0 = 这一瞬间过期了（或行被清理任务删了）→ 400。
计数在库里加，不是"读出来 +1 写回去"（并发会丢计数）。

**领取和导入同一条事务**：`claim()` 不 commit，由调用方提交。
顺序是"先占一次领取 → 再导入"：导入炸了整条事务回滚，码还在，用户可以再来一次。
导入本身直接调 `app/imports/service.py: run_import`，没有第二份实现 ——
幂等、撤销、批次报告、图片落盘、认不出的角色照样保留，两条入口行为完全一致。

## 5. 老客户端兼容层（线上 3.2.0–3.2.2）

老客户端是 `XMLHttpRequest` 打的 `POST https://local.peilika.beer/upload`：

- `Content-Type: application/json`（**非 simple request → 会发 OPTIONS 预检**）
- body = 导出包 JSON 原文（不是 multipart、不是 `{file:…}`）
- 期望响应字段一个不能少：`code` / `bytes` / `raw_bytes` / `uploaded_at` /
  `cleanup_at` / `keep_hours`
- 错误映射：413 → 「超过 64MB 上限」；404（/fetch）→「取件码不存在或已清理」；429 →「太频繁」

### POST /upload

```http
POST /upload
Content-Type: application/json
<导出包 JSON 原文>
```

```json
200 OK
{
  "ok": true,
  "code": "AB3D7K9Q",
  "bytes": 12345,
  "raw_bytes": 12345,
  "uploaded_at": "2026-11-18 00:31:07",
  "cleanup_at": "2026-11-19 00:31:07",
  "keep_hours": 24
}
```

刻意宽松：**不校验包结构**（老客户端改不了，服务端挑刺等于让云同步断掉）、
**不要登录**（老形状里没有账号/设备概念）、**额度更宽**（每 IP 每小时 30 个包）。

`ok: true` 是线上成功响应本来就有的字段（对拍脚本按它判成功），我们照带。

### POST /fetch

```json
请求：{"code": "AB3D7K9Q"}
200：Content-Type: application/json; charset=utf-8，body = 导出包原文（逐字节相同）
400：{"ok": false, "error": "缺少取件码"}      ← 空码/没给码
404：{"ok": false, "error": "取件码不存在或数据已被清理（保留 24~48 小时）"}
429：{"ok": false, "error": "请求太频繁，请稍后再试"}
```

`/fetch` **不做导入**：老客户端拿到包自己解析。它只做"判过期 + 记一次领取 + 原样返回字节"。
不 re-serialize、不加 BOM、不加 `Content-Encoding`（没有 gzip）——
客户端直接 `JSON.parse`，多一个字节都可能失败。

### 共用一套存储

新老两套接口用**同一张表、同一批文件**：`/upload` 传的包能在
`GET /v1/uploads/{code}` 查到；`/v1/uploads` 传的包能被 `/fetch` 取回。
这样把 `local.peilika.beer` 指到新后端，老客户端一行不用改。
（`tests/test_legacy_upload.py` 里两个方向都有用例。）

### 老接口的错误形状（重要）

**所有**错误都是 `{"ok": false, "error": "<中文>"}`，没有 `request_id`、没有嵌套
`error.code`。原因：老客户端对没专门映射的错误，会把响应体前 120 字直接贴在界面上
（`cloudData.ts:184`）。给它看新接口那套 `{"error": {...}, "request_id": ...}`，
用户看到的就是一坨 JSON —— 这是兼容 bug，不是审美问题。

实现：`LegacyError(AppError)` + `main.py` 里注册的独立 handler。`/v1/uploads*`
继续用新形状。

### 与线上旧服务的对拍结果（已核对，`原始网站前后端/upload-service/docs/契约.md`）

| 项 | 我们的做法 | 说明 |
|---|---|---|
| 成功字段 | `ok/code/bytes/raw_bytes/uploaded_at/cleanup_at/keep_hours` | 一个不少；`keep_hours` 是 int（JS 显示 24 没问题） |
| 时间格式 | `YYYY-MM-DD HH:MM:SS`，**CST（UTC+8）无时区** | 线上就是服务器本地时间，给 UTC 会差 8 小时 |
| `bytes` / `raw_bytes` | 两者都 = 请求体字节数 | 线上 `bytes` 是 gzip 后大小；我们不 gzip，所以两个数一样 |
| 单包上限 | `import_max_bytes`（默认 64MB），判定 `>`（等于 67108864 放行） | 和线上一致 |
| TTL | `upload_ttl_hours`（默认 24h） | 不短于线上 |
| 上传频率 | 老接口 30 次/小时/IP；新接口 5 次/小时/IP | 线上 `/upload` 完全不限速；我们按产品要求加了闸门 |
| 取件频率 | 30 次/**分钟**/IP（60 秒窗口） | 和线上同值同窗口 |
| 码字符集 | `ABCDEFGHJKLMNPQRSTUVWXYZ23456789`（同线上 32 字符表，保留 L） | 老客户端校验认 L，去掉会让它判"格式不对" |
| 码的归一化 | 只 `strip + upper`；长度≠8 或字符集不符 → 404，**不静默过滤字符** | 线上会过滤非法字符，导致过"多打一个字符取到别人的包"，不复刻 |
| 清理时刻 | `cleanup_at` = 上传时刻 + 24h | 线上是"下一个 12:00 检查点"；我们不做那个语义（界面写着保留 24 小时，就该真是 24 小时） |
| 码进日志 | 只打前 2 位（`YD***`），路径和 uvicorn 访问日志也打码 | 线上打了完整码，谁看日志谁能取走包 |

### 日志里的码

`app/uploads.py: code_hint()` 只留前 2 位；`main.py` 里还有一个日志过滤器
（`_UploadCodeRedactor`）兜底：`/v1/uploads/AB3D7K9Q` 这种路径无论被谁打进日志，
都会被改成 `/v1/uploads/AB***`（包括 uvicorn 自己的访问日志）。
`tests/test_legacy_upload.py::test_logs_never_contain_full_code` 用 `caplog` 守着这条。

## 7. 限流 / 额度 / 清理

| 项 | 默认值 | 配置名 |
|---|---|---|
| 码有效期 | 24 小时 | `upload_ttl_hours` |
| 新接口上传频率 | 5 个/小时/IP | `upload_rpm` |
| 老接口上传频率 | 30 个/小时/IP | `legacy_upload_rpm` |
| 取件频率 | 30 次/**分钟**/IP | `fetch_rpm` |
| 全站取件区总量 | 2 GB | `upload_total_bytes` |
| 单包上限 | 64 MB | `import_max_bytes`（和 /v1/imports 共用） |

限流是**进程内固定窗口**（和项目其它限流一致），重启清零、单进程有效。
按 IP 限流的前提是**从 `request.client.host` 能拿到真实客户端 IP**：
uvicorn 默认 `proxy_headers=True`、`forwarded_allow_ips=127.0.0.1` ——
反代（nginx/CF Tunnel）在本机时它会按 `X-Forwarded-For` 还原真实 IP；
如果反代在 Docker 网桥里（不是 127.0.0.1），必须显式给
`--forwarded-allow-ips=<反代地址>`，否则所有人共用一个"127.0.0.1"桶。
线上老服务就是因为这一点导致"两个用户同时取件互相 429"（契约 §1.7）。

清理两条路：

1. `POST /v1/uploads`、`POST /upload` 每次顺手清最多 20 条过期记录（`lazy_cleanup`），
   失败了也不影响这次上传；
2. `scripts/cleanup_uploads.py` 全量清（建议 crontab 每小时）：

```bash
python scripts/cleanup_uploads.py --dry-run   # 只看有多少可清
python scripts/cleanup_uploads.py             # 真清（删行 + 删文件 + 扫 .part 残留）
```

清理规则：`expires_at <= now` 或 `last_claimed_at <= now - TTL`。
顺带删掉 `<upload_dir>/tickets/*.part`（上次进程被 kill 时正在传的那半个包）。

## 8. 写盘与回滚

- `/v1/uploads`（multipart）：和 `/v1/imports` 一样，读进内存后 `write_bytes`。
- `/upload`（老接口）：**分块写临时文件**（`tickets/.upload-*.part`）→ 插库拿码 →
  `Path.replace` 改名成 `<code>.bin`。峰值内存是 1MB 块，不是 64MB。
- 任何一步失败：
  - 插库后写盘失败 → 删掉可能写了一半的目标文件，异常抛出，事务不提交；
  - 写盘成功但 `commit` 失败 → `commit_or_discard` 删掉文件再抛（不留孤儿文件）。

## 9. CORS

`app/main.py` 里装了 `CORSMiddleware`：`allow_origins=["*"]`、`allow_methods=["*"]`、
`allow_headers=["*"]`、`allow_credentials=False`。

为什么是 `*` 而不是白名单：客户端 origin 不固定（APK WebView 是 `https://localhost`、
网页是另一个域、EXE 是 `file://`、还可能有自建反代）。鉴权走 Bearer token 而不是 cookie，
所以 `*` 不会让任意站点拿用户身份发请求。代价是 `allow_credentials` 必须为 False
（规范上带 cookie 的跨域不允许配 `*`）。

## 10. 已知风险 / 没做的事

1. **`/v1/uploads` 的 64MB 仍然读进内存**（和 `/v1/imports` 一致）。老接口已经改成流式落盘；
   新接口要改得先改 `imports/package.py`（它只吃 `bytes`），这一轮没动。
2. **按 IP 限流依赖反代配置**：uvicorn 不开 `--proxy-headers` 时所有请求的 IP 都是反代地址。
3. **码可重复领** = 拿到码的人都能拿到那份数据（24 小时内）。这是产品口径，不是漏洞；
   但码只有 32^8 种，**没有针对"猜码"的专门限流**（只有 `/fetch` 30 次/分钟、
   `/v1/uploads/claim` 无独立限流）。数据包里有聊天记录，后续如果介意，应该给 claim 加限流。
4. **`upload_tickets` 不加外键**：设备/账号/批次都可能被删，这行要留着给运维查。
5. **清理只按 TTL**：`expires_at` 被人手工改坏时，靠 `created_at` 索引兜底（没有自动修）。
6. **没有 gzip 存储**：线上旧服务落盘前会 gzip（`bytes` 是压缩后大小）。我们不压 ——
   磁盘够用，多一层就多一处坏法；代价是老接口的 `bytes` 和 `raw_bytes` 相等（客户端只展示）。
7. **`/v1/uploads` 的 `expires_at` 是 ISO UTC**（带 `+00:00`），只有老接口的
   `uploaded_at`/`cleanup_at` 是 CST 无时区字符串。两种形状是故意的：新客户端认 ISO，
   老客户端只认它原来那套。
8. 没做：断点续传、上传进度接口、码的自助更换、按账号查"我领过哪些包"、gzip 落盘。

## 11. 部署注意（接线上域名之前看一遍）

| 项 | 要做什么 | 为什么 |
|---|---|---|
| 反代 body 上限 | nginx 配 `client_max_body_size 64m` | 应用侧会回 413，但别让 64MB+ 先整个进内存（线上是 nginx 挡的） |
| 真实 IP | uvicorn `--forwarded-allow-ips=<反代地址>`（反代不在 127.0.0.1 时） | 否则所有请求的 IP 都是反代地址 → 全站共用一个限流桶 → 两人同时取件互相 429 |
| 定时清理 | crontab 每小时跑 `scripts/cleanup_uploads.py` | 惰性清理每次只清 20 条；没人上传时它永远不跑 |
| 文件权限 | 保持默认（文件 644 / 目录 755），**别用 777** | 线上老服务是 777：本机任何用户可读所有人的导出包 |
| 访问日志 | 不用关；`_UploadCodeRedactor` 会把码打码 | 关掉会丢排查信息，打码就够了 |
| `/stats` | 不做 | 只给线上 monitor 面板用；新后端有 `/health`，运维别把码吐出来 |
