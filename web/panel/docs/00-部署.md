## 3. 上传（原子切换，别原地覆盖）

原地 `rsync --delete` 覆盖 dist 有个坑：新旧 `index.html` 与新 `assets/*.js` 会在几秒内不匹配，
正在打开页面的人会拿到 404 的 JS（白屏）。所以走"新目录 + 改名"：

```bash
# 1) 本地打包（只带 dist，不带 node_modules / src）
cd web/panel
tar -czf /tmp/panel-dist-$(date +%Y%m%d%H%M).tgz dist

# 2) 传到构建机（按你实际线路；以下是 scp 形态）
scp /tmp/panel-dist-*.tgz  <user>@<host>:/tmp/

# 3) 服务器上解到临时目录
ssh <user>@<host> 'set -e
  cd /var/www/panel.peilika.beer
  rm -rf dist.new && mkdir dist.new
  tar -xzf /tmp/panel-dist-*.tgz -C dist.new --strip-components=1
  test -f dist.new/index.html            # 没这个文件就说明解错了，立刻退出
  chown -R www-data:www-data dist.new'

# 4) 原子换名（同一条命令里完成，中间没有"半个站点"的窗口）
ssh <user>@<host> 'set -e
  cd /var/www/panel.peilika.beer
  rm -rf dist.prev
  mv dist dist.prev
  mv dist.new dist'

# 5) 静态文件不需要 reload nginx
```

> 为什么不用 `cp -r dist/* /var/www/...`：`index.html` 是"这一版用哪个 JS"的入口，
> 它被覆盖的那一刻如果 JS 还没传完，访客看到的就是白屏。

## 4. vhost

```bash
# 1) 放配置（内容见仓库 web/panel/nginx/panel.peilika.beer.conf）
sudo cp web/panel/nginx/panel.peilika.beer.conf /etc/nginx/sites-available/
sudo ln -sf /etc/nginx/sites-available/panel.peilika.beer.conf /etc/nginx/sites-enabled/

# 2) 语法检查 —— 必须先过这一关再 reload
sudo nginx -t

# 3) 生效（reload 不掐断现有连接）
sudo systemctl reload nginx
```

配置里已经写好的三件事（改之前先读文件顶部的注释）：

1. `root` 指到 `dist` 这一层（不是它的父目录）；
2. `/v1/` 反代到 `127.0.0.1:5660`，URI 原样透传；
3. `index.html` 强制 `no-store`，`/assets/*` 一年长缓存。

**HTTPS**：如果 `panel.peilika.beer` 走 Cloudflare 橙云，TLS 在外层，本机只写 80 即可
（Cloudflare 的"灵活/完全"模式按你现有站点的规矩来）。如果这台机自己终止 TLS，
把文件末尾注释掉的 443 server 块打开、填证书路径。

## 6. 回滚

静态站回滚（10 秒，无需 reload）：

```bash
cd /var/www/panel.peilika.beer
mv dist dist.broken && mv dist.prev dist
```

nginx 配置回滚：

```bash
sudo rm /etc/nginx/sites-enabled/panel.peilika.beer.conf
sudo nginx -t && sudo systemctl reload nginx
```

后端回滚与面板无关（面板只是 `/v1` 的调用方）。注意：如果后端回退到**没有 `/v1/admin/*`
的旧版本**，面板会看到一批 404，这时应当同时把面板下线（`redis` 不用动，直接删 enabled 软链）。

## 7. 故障排查

| 现象 | 最可能的原因 | 怎么确认 |
| --- | --- | --- |
| 打开是 nginx 默认页 | `root` 指错一层（指到 `.../panel.peilika.beer` 而不是 `.../dist`） | `curl -I` 看有没有 `index.html` 里的 `<title>` |
| 页面标题对、但整页空白 | `assets/*.js` 404（上一版 index.html 配了新 JS，或 base 不是 `/`） | 浏览器 Network 里看 JS 的状态码 |
| 刷新深链接 404 | `location /` 的 `try_files` 被覆盖了 | `curl https://.../users` 应回 200 + HTML |
| 登录一直提示过期 | `/v1` 反代 502 或没透传 `Authorization` | 直接 `curl` 第 5 节②那条 |
| 登录成功但显示"无权限" | 这个账号 `role` 不是 admin | 服务器上 `scripts/make_admin.py --list` |
| 数字不更新 | nginx 或浏览器缓存了 `/v1` 响应 | 看响应头 `cache-control: no-store` |
| 改了面板但没生效 | `index.html` 被缓存 / 只传了 assets 没换 index | 强制刷新一次，再按第 3 节重新切目录 |
| 界面是旧的、数据是新的 | 就是上一行：跑的是旧 JS | 同上 |

## 8. 账号与安全

**管理员从哪来**：后端没有"第一个注册的人是管理员"这种设计（防抢号），必须手工提权：

```bash
cd web/back
.venv/bin/python scripts/make_admin.py --username 你的用户名     # 提权
.venv/bin/python scripts/make_admin.py --list                    # 看现在有谁
.venv/bin/python scripts/make_admin.py --username 某人 --revoke  # 收回
```

**面板的登录机制**（容易误会，写清楚）：

1. `POST /v1/auth/device` 拿一张**设备 token**（这是唯一的凭证形态，后端没有"登录发 token"）；
2. `POST /v1/auth/login` 把这张设备 token 挂到账号上；
3. 之后所有 `/v1/admin/*` 请求带 `Authorization: Bearer <这张 token>`；
4. **登录响应里没有 `role`** —— 所以面板在登录成功后会再打一次后台接口：200 才算管理员，
   403 就提示"这个账号不是管理员"并立刻退出（token 一起清掉）。

其它几条：

- token 存在 `localStorage`（`baker.panel.token`），**任何代码都不会把它打到 console**；
- 设备 token 不会过期，所以公用电脑上用完必须点「退出」（退出会解绑设备并清本地 token）；
- 密钥页**只显示状态**：后端 `GET /v1/admin/keys` 连密文都不返回，页面里没有任何可显示的密钥字段；
- 面板页面带 `X-Frame-Options: DENY` 与 `X-Robots-Tag: noindex`，没有被嵌 iframe 和被搜索引擎收录的余地。

**本地联调用的测试账号**（只在 `baker_back` 库里，别拿去生产）：

| 用户名 | 密码 | 角色 | 用途 |
| --- | --- | --- | --- |
| `panel_admin` | `PanelAdmin2026` | admin | 面板联调主账号，`public_id=abc03cd516a149119c619f35b3621178` |
| `panel_visitor` | `Visitor2026` | user | 只用来验证"登录成功但不是管理员 → 拦下并登出"这条路 |

> 生产要另建一个自己的管理员账号；这两个账号建议在面板上线前 `--revoke` 或直接停用。
>
> 附带说明：`panel_admin` 名下的 `devices` 会比常人多（每次无头浏览器走查都是一个全新
> profile = 一台新设备）。不影响使用，想清掉可以在 `baker_back` 里删掉
> `platform='web-panel'` 且 `owner_user_id=<panel_admin 的 id>` 的设备行。
