# 06 · 旧版本地数据迁移

> 2026-11-18 · 对应代码：`src/utils/legacyLocalCore.ts`（纯函数）、
> `src/utils/legacyLocalData.ts`（浏览器胶水）、
> `src/components/layout/LegacyMigrateBanner.vue`（入口条）、
> `scripts/legacy-migrate-smoke.mjs`（自测 22 项）。
>
> 目标：**新 web 端能完美读到老 web 存在用户本地的数据，并一条不丢地迁到新后端**。
> 老数据**只读**：不删库、不删 key、不改老 key 的内容；迁移失败不写标记、可无限重试。

---

## 0. 结论速览

| 问题 | 答案 |
|---|---|
| 老数据存在哪 | 浏览器 IndexedDB `endfield-baker` / object store `data`（**按 origin 隔离**） |
| 线上跑的是哪条线 | `chat.peilika.beer` → `/var/www/peilika-chat` → **web31 / 3.1.0** |
| 3.2.2 线在哪 | `test2.peilika.beer` → `/var/www/peilika-v2` |
| 两条线的库名/表名 | **完全相同**（`endfield-baker` / `data`），都是无版本号打开（首次创建 = version 1） |
| 两条线的卡片键 | 3.1：只有 `cards`；3.2.2：新增 `cardsV2` + `card:<slot>` 分片，`cards` 退化为**不再更新的旧快照** |
| 老网页和 Electron/APK 同一套 key 吗 | **是**。打包端把同一批键名存进 `endfield-baker-data.json`（`utils/nativeStorage.ts`） |
| 迁移主路径 | 同 origin 直读 IndexedDB（不写死域名）→ 拼包 → `POST /v1/imports` |
| 兜底路径 | 读不到 / 库损坏 / 单条超 64MB → 「先备份一份」+「数据管理 → 导出数据」再导入；>64MB 会自动分批 |
| 迁移标记 | `localStorage['bakerai.legacy-migrated.v1'] = {batchId,batchIds,at,counts}`（**新 key**） |
| 会不会删老数据 | **不会**。任何情况下不 `deleteDatabase`、不 `removeItem` 老 key |

## 1. 老网页版的持久化层（IndexedDB）

### 1.1 库、表、打开方式

来源：`web31/src/composables/useChatPersistence.ts`（3.1.0，线上）与
`v322kit/src/composables/useChatPersistence.ts`（3.2.2）—— 两边的这一段**常量逐字相同**：

```ts
const DB_NAME = 'endfield-baker'
const STORE_NAME = 'data'
const request = indexedDB.open(DB_NAME)   // 不带版本号 → 首次创建为 version 1
request.onupgradeneeded = () => {
  if (!db.objectStoreNames.contains(STORE_NAME)) db.createObjectStore(STORE_NAME)
}
```

* **没有 keyPath**：所有键都是**外部键**（`store.put(value, key)`），一个对象仓库装全部数据。
* 网页端与打包端共用**同一批键名**：打包端 `createNativeStore` 把 `{key: value, ...}` 整个
  JSON 序列化进 `endfield-baker-data.json`（同目录 `.bak` 一代备份）。
* 3.2.2 的 `cards` 分片格式见 §1.4；3.1 **没有**分片。

### 1.2 键清单

| key | 写入者 | 值 |
|---|---|---|
| `cards` | 3.1 全量；3.2.2 只作为回退快照（迁移后不再更新） | `Card[]` |
| `cardsV2` | 仅 3.2.2 | `{ v: 2, slots: number[], next: number, keys: string[] }` |
| `card:<slot>` | 仅 3.2.2 | 单张 `Card` |
| `settings` | 两边 | 设置快照对象（§1.5） |
| `myGender` | 两边 | `'male' \| 'female'` |
| `stripVariant` | 两边 | `0 \| 1 \| 2`（顶部聊天条图片下标） |
| `version` | 两边 | `number`（`PROJECT_VERSION = 1`） |
| `usage` | 两边 | 用量统计快照（§1.6） |
| `cardActivity` | 两边 | `Record<string, number>`（卡片身份 → 最后活跃 ms） |
| `subActivity` | 仅 3.2.2 | `Record<string, number>`（`卡片身份#子对话下标` → ms） |

> `card:<slot>` 的 slot 编号**落盘后不再重排**（删卡只删键），所以索引里的 `slots`
> 就是卡片在列表里的顺序；`keys` 是同一顺序的卡片身份（`s:角色名` / `g:成员|成员`），
> 用来校验"位置 → slot"没串号。

### 1.3 值形状（真实形状，来自 `types/chat.ts` 与 `sanitizeCards` 白名单）

```ts
interface Card {
  conversations: Conversation[]          // 长度 ≥ 1
  members?: string[]                     // 群聊成员；长度 ≥2 才算群聊（卡片级）
  myRole?: 'admin' | 'observer' | string // 群聊里"我"的身份；其他字符串 = 扮演该角色
  speakMode?: 'round' | 'smart' | 'assign'  // 3.1/3.2.2 只有三种；新前端多了 'weighted'
  assignTarget?: string
  groupRunning?: boolean
  groupTopic?: string
  groupSessionId?: string                // 刻意不持久化（后端 300s 回收），实际库中通常没有
}

interface Conversation {
  name: string                           // 角色名 / 群聊显示名
  messages: ChatMessage[]
  contextHistory?: ContextEntry[]        // undefined = 旧数据未初始化；[] = 显式清空过
  sessionOutputTokens?: number           // 累计输出 token（两边都有）
  promptTokens?: number                  // ↓ 以下四个是 web31(3.1) 独有的 token/总结账本
  lastPromptTokens?: number
  summaryAnchor?: number
  compactedBefore?: number
  suggestions?: { forMessageId: number; items: string[]; at: number }
}

interface ChatMessage {
  id: number                             // 对话内序号（v-for key，不是全局 id）
  side: 'other' | 'mine'                 // other=左侧气泡 / mine=右侧
  text: string
  image?: string                         // dataURL（纯图消息 text 通常为 ''）
  imageW?: number
  imageH?: number
  topic?: boolean                        // 群聊「新话题」提示行：屏上显示、不进 AI 上下文
  summary?: boolean                      // web31 「对话总结」卡片（3.1 新架构）
  speakerName?: string                   // 群聊说话人
  speakerAvatar?: string                 // 头像快照（导出时会丢掉，导入按名字重查）
  mood?: string                          // 表情 token，如 sns_emoji_001
  isError?: boolean                      // 请求失败占位气泡（持久化前会被过滤）
  regenerateUserId?: number
}

interface ContextEntry {
  side: 'other' | 'mine'
  text: string
  image?: string                         // dataURL
}
```

```json
      "messages": [

```

**群聊带 speaker / 话题行**（卡片级元数据在 `Card` 上，不在 conversation 里）：

```json
{

          "speakerName": "伊冯", "mood": "sns_emoji_001" }
      ]
    }
  ]
}
```

**清空过消息、只剩 AI 记忆**：

```json
{
  "conversations": [
    {
      "name": "佩丽卡",
      "messages": [],
      "contextHistory": [
        { "side": "mine", "text": "上次说到哪了？" },
        { "side": "other", "text": "说到你会记得我。" }
      ]
    }
  ]
}
```

**3.2.2 分片**（`cardsV2` + `card:0`）：

```json
// key: cardsV2
{ "v": 2, "slots": [0, 1], "next": 2, "keys": ["s:伊冯", "s:佩丽卡"] }
// key: card:0  → 就是上面那种 Card
// key: cards   → 升级到 3.2.2 那一刻的整库快照（之后不再更新，但仍保留作回退）
```

> ⚠️ **这是"完美读到"的关键坑**：3.2.2 升级后，新消息只写 `card:N`；`cards` 停在
> 升级那一刻。只读 `cards` 会"看起来丢了升级后的聊天记录"。迁移器**两个都读**并按
> 消息 id / 内容去重合并（见 §5.3）。

## 3. 线上 web31 与 3.2.2 的本地存储差异 × 迁移策略

> 逐文件核对：`web31/src`（3.1.0，chat.peilika.beer）vs `v322kit/src`（3.2.2，test2.peilika.beer）。
> **结论：不是"本质不同"，是同一条线的两代** —— 库名、表名、卡片/消息/对话形状、
> 设置快照、导出包格式全部兼容；差异只在"多/少几个键和账本字段"。

### 3.1 逐项对照

| 项 | web31（3.1，线上） | v322kit（3.2.2） | 迁移器怎么做 |
|---|---|---|---|
| IndexedDB 库名 / store | `endfield-baker` / `data` | **相同** | 同一套读取器；按库名前缀多收兄弟库（正常只有一个） |
| 卡片键 | `cards`（整库） | `cards` + `cardsV2` + `card:<slot>` | 两处都读、按消息去重合并（§5.3） |
| `cards` 的语义 | 当前全量 | 升级瞬间的旧快照（不再更新） | 同上；只读 `cards` 会漏 3.2.2 升级后的消息 |
| `subActivity` | 无 | 有 | 不迁移（列表排序偏好） |
| `cardActivity` | 有 | 有 | 不迁移（列表排序偏好） |
| `settings.promptOverrides` | 有 | 有 | **迁**→ `device_prompts` |
| `settings` 其余字段 | 有（少 2 项） | 有（多 `keepDeltasOnEmptyDone`/`immersiveStrip`） | 不迁移（新客户端不沿用旧客户端配置） |
| `messages[].summary`（对话总结卡片） | **有**（3.1 总结新架构） | 无（3.2.2 不再写这个标记） | 迁成 `side='system'`：屏上保留、不进 AI 上下文 |
| `conversation.sessionOutputTokens` | 有 | 有 | 不迁移（token 账本） |
| `conversation.promptTokens` / `lastPromptTokens` / `summaryAnchor` / `compactedBefore` | **有** | 无 | **读但不迁**：新后端自己算压缩；保留在老库不动 |
| `GroupSpeakMode` | 3 种（round/smart/assign） | 3 种 | 原样透传；新后端也认 `weighted`（新前端建的群） |
| `endfield-baker-announcement-read` | **有** | 无 | **读但不迁**：公告已读是 UI 状态，不属聊天数据；新前端同 origin 继续读同一个 key |
| `endfield-baker-prompt-tokens-measured` | **有** | 无 | **读但不迁**：本机实测值，新前端继续读同一个 key |
| `endfield-baker-char-names` | 只剩注释 | 无 | 忽略（死键） |
| `keep-deltas` / `immersive-strip` | 无 | 有 | 不迁移（设置项） |
| 导出包（ZIP/JSON） | 同格式（v7 `order` 也有） | 同格式 | 兜底路径共用同一后端解析器 |
| 打包端（EXE/APK） | 同一套 key → `endfield-baker-data.json` | 同 | 逻辑共用；网页端读不到文件，走导出包 |

### 3.2 "两个库名都要试"这件事的实际情况

* 两条线**库名完全一样**（已逐字核对），所以不存在"两个库名"。
* 真正的隔离是 **origin**：`chat.peilika.beer` 与 `test2.peilika.beer` 是两个网站，
  各自的 IndexedDB 互不可见。用户在两个域都开过时，当前 origin 只能读到**自己那份**；
  **另一份不会被碰**（也读不到），这正好符合"优先迁当前 origin、另一份不碰"。
* 代码仍按前缀 `endfield-baker` 枚举当前 origin 的库（`indexedDB.databases()` 可用时），
  万一将来某条线改名，读取器不至于只认死名字；多读出来的库会按卡片身份合并去重。

> ⚠️ **界面显示的一个已知空窗**：新前端的基座是 web31（3.1）—— 它自己的
> `useChatPersistence` 只读 `cards`。所以如果新前端被部署到 **3.2.2 的 origin**
> （test2）上，列表会先显示"升级那一刻的旧快照"，升级后的消息在 `cardsV2` 分片里
> 暂时不显示（**数据没丢**，迁移器读的是并集）。这属于"列表改服务端驱动"要解决的
> 显示问题，不在本迁移器里改本地持久化层（避免和列表改造撞车）。

### 3.3 只在 web31 存在的东西，明确处理

| 东西 | 处理 | 为什么 |
|---|---|---|
| `messages[].summary` | **迁**成 system 角色消息 | 它是"屏上能看、但不是谁说的话"的卡片；system 侧新后端不喂模型，语义正好 |
| `conversation.promptTokens/lastPromptTokens/summaryAnchor/compactedBefore` | **读但不迁** | 新后端的压缩/预算由服务端算，这些账本只对老前端有意义；留着不影响任何消息 |
| `endfield-baker-announcement-read` | **不迁** | 公告已读是 UI 状态；新前端（同一线）继续读同一个 localStorage key，本来就在 |
| `endfield-baker-prompt-tokens-measured` | **不迁** | 本机测量值；同上，新前端继续用 |
| `endfield-baker-char-names` | **忽略** | 源码里只剩注释，没有任何读写 |

## 4. 导出包格式（兜底路径 / 「先备份一份」用）

老站「数据管理 → 导出数据」有两种，新后端**两种都吃**（按内容判断，不看扩展名）：

### 4.1 `.zip`（推荐，图片独立）

```
project.json                          version / myGender / stripVariantIndex / stats /
                                      cards[]（群聊卡片级元数据，下标与 cards/NN 对齐）/
                                      settings / order
cards/00/conversations/00-伊冯.json    { name, messages, contextHistory?, … }
cards/00/images/00-3.png              图片本体（JSON 里只留 ZIP 内路径）
prompts/characters/伊冯.txt           用户改过的角色提示词（仅自定义时）
```

### 4.2 `.json`（单文件，图片 dataURL 内联）

```jsonc
{
  "version": 1,
  "cards": [ { "conversations": [ { "name": "伊冯", "messages": [ … ] } ] } ],
  "myGender": "male",
  "promptOverrides": { "伊冯": "……" },
  "settings": { "…": "…" },
  "order": ["s:伊冯", "g:伊冯|佩丽卡"]
}
```

本迁移器的「先备份一份」导出的就是 **4.2 这个形状**（可直接再导入新后端）。

## 5. 迁移实现

### 5.1 文件与职责

| 文件 | 职责 |
|---|---|
| `src/utils/legacyLocalCore.ts` | **纯函数**（零 import，Node 可直接跑）：归一化、分片合并、统计、转导入包、自动分批、上传编排、标记读写、文案 |
| `src/utils/legacyLocalData.ts` | 浏览器胶水：打开 IndexedDB（多库/分片/旧快照）、读 localStorage、读打包端 JSON 文件、调 core、清理老 SW |
| `src/components/layout/LegacyMigrateBanner.vue` | 顶部提示条：检测 → 立即迁移 / 先备份一份 / 稍后再说 → 进度 → 摘要 / 错误 |
| `src/App.vue` | **只加一行挂载** `<LegacyMigrateBanner />`（+ 一行 import） |
| `scripts/legacy-migrate-smoke.mjs` | 22 项自测：转换断言 + 假后端真 HTTP + 分批 + 失败路径 |

> 没有改 `stores/chat.ts`、`composables/useChatPersistence.ts`、`DataManagerDialog.vue`、
> `SettingsDialog.vue`、`utils/cloudData.ts`（同事的取件码功能区域）。

### 5.2 对外能力

```ts
// 只读检测（不改不删）；返回 {cards,conversations,messages,hasData,...}
detectLegacyLocal(): Promise<LegacyDetectSummary & { local }>

// 本地数据 → 最小导入包（{version:1,cards:[...],myGender,promptOverrides}）
toImportPackage(local): Blob
toImportPackageJson(local): string

// 迁移（确保 token → 上传 → 写标记；失败不写标记）
migrateLegacyLocal({ onProgress?, force? }): Promise<MigrationOutcome>

// 覆盖部署前给用户留底
downloadLegacyBackup(): Promise<{filename,bytes,counts}>

// 老 SW / Cache 清理（同一浏览器只清一次）
cleanupLegacyServiceWorkersOnce(): Promise<boolean>
```

### 5.3 读取：两个来源都要，合并去重

1. **打包端**（`getNativeFileBridge()` 有值，即 EXE/APK）：直接读
   `endfield-baker-data.json` 的 `cards`（打包端从没用分片）。
2. **网页端**：枚举当前 origin 下 `endfield-baker*` 的库；每个库读
   * `cardsV2` + `card:<slot>`（3.2.2 分片，最新消息在这里）
   * `cards`（3.1 全量 / 3.2.2 的旧快照）
   * `settings` / `myGender`

合并规则（`mergeLegacyCards` / `mergeMessages`）：

* 卡片身份：群聊 = **成员集合**（排序后），单聊 = **第一个子对话的名字**。
* 同一身份的两张卡：按子对话**位置**合并（长度一致时）；长度不一致时按
  "名字相同 + 消息有交集"匹配，匹配不到就**追加**（多一段重复，好过多丢一段）。
* 消息：按 `id + 内容指纹` 去重；**同一个 id 但内容不同 → 两条都留**，后来者分配
  新 id 追加（删过存档导致下标错位时不会互相覆盖）。
* `contextHistory`：两边取并集（按内容去重），保留更多记忆。
* 分片内部出现同身份的两张卡时保留成两张，不合并。

### 5.4 转换：老字段 → 新后端

| 老本地字段 | 新后端 | 规则 |
|---|---|---|
| `messages[].side: mine/other` | `messages.role: user/assistant` | 直接映射 |
| `messages[].topic: true` | `role: system` | 屏上显示、`messages_repo` 取上下文时跳过 system |
| `messages[].summary: true`（3.1） | `role: system` | 同上，总结卡片不喂模型 |
| `messages[].isError` | **丢弃** | 请求失败占位不是聊天记录；计入"本地跳过" |
| `messages[].text` 为空且无图 | **丢弃** | 空消息没有信息；计入 skipped |
| `messages[].image`（dataURL） | `messages.image` 原样内联 | 后端 `imports/images.py` 解 dataURL 落附件 |
| 图片不是 dataURL（ZIP 路径 / avif/heic/bmp/svg） | 丢图，文字保留 | 后端只认 png/jpeg/webp/gif；有图无字时补 `[图片]` |
| `messages[].speakerName` | `speakerName` | 群聊说话人；单聊缺省时后端用角色名 |
| `messages[].mood` | `mood` | 原样 |
| `conversation.contextHistory` | **原样带上** | 屏上消息为空 → 后端用它兜底；屏上有消息 → 后端计入 `dropped_context` 并写进 notes |
| `conversation.name` | 会话标题 / 角色名 | 空名字的对话跳过（后端也会丢） |
| `Card.members`（≥2） | `mode='group'` + 成员 | 卡片级字段，漏了群聊会退化成单聊 |
| `Card.myRole` | `player_role` | 自由文本，截 64 字符 |
| `Card.speakMode` | `speak_mode` | round/smart/assign/weighted 都认（非法值后端降 smart） |
| `promptOverrides` | `device_prompts` | **只影响这台设备**，不动角色全局人设；空串不传 |
| `myGender` | 批次报告 | 新后端没有这个状态，不落库 |
| `order` / `cardActivity` / `subActivity` | 不迁 | 列表排序偏好；导入时按 cards 数组顺序给 `last_active_at` 递减 |
| `settings`（除 promptOverrides） | 不迁 | 客户端本地配置，新客户端不该沿用 |
| `stripVariant` | 不迁 | 聊天条图片下标（纯 UI） |
| `usage` | 不迁 | 本机用量统计 |
| `suggestions` / `sessionOutputTokens` / `promptTokens` / `lastPromptTokens` / `summaryAnchor` / `compactedBefore` | 不迁 | 一次性缓存 / 老前端账本 |
| `speakerAvatar` / `imageW` / `imageH` / `regenerateUserId` / `groupRunning` / `groupTopic` / `assignTarget` / `groupSessionId` | 不迁 | 显示层 / 运行时状态；新后端没有对应字段（**不自己造字段**） |

### 5.5 流程（检测 → 提示 → 转换 → 上传 → 标记 → 摘要）

```
应用启动
  └─ LegacyMigrateBanner.mount
       ├─ cleanupLegacyServiceWorkersOnce()      // 覆盖部署善后（只做一次）
       ├─ 有 bakerai.legacy-migrated.v1 ? → 不出现
       ├─ 本次会话点过"稍后" ? → 不出现
       └─ detectLegacyLocal()（只读）
            ├─ 无数据 → 不出现（新用户）
            └─ 有数据 → 顶部条："发现旧版本地数据：N 张卡 / M 段对话 / K 条消息"

点「立即迁移」
  ├─ readLegacyLocal()                 // 分片+旧快照合并、localStorage 提示词兜底
  ├─ buildImportPackage()              // 只翻译字段；isError/空消息丢弃并计数
  ├─ splitImportPackage()              // ≤64MB 一批；超了按 卡→对话→消息 自动分批
  ├─ ensureDeviceToken()               // 没有就静默 POST /v1/auth/device
  ├─ 逐批 POST /v1/imports              // multipart: file + mode=merge，带 Bearer
  │     （浏览器用 XHR 拿真实上传进度；Node/自测走 fetch）
  ├─ 201 → 累加 counts / notes / batchIds
  ├─ 成功：写 bakerai.legacy-migrated.v1 = {batchId,batchIds,at,counts}
  │         + forgetAllBindings()（下次发消息重新绑到带历史的会话）
  └─ 失败：不写标记；提示原因 + 「重试」+「先备份一份」
```

**幂等**：后端用包内容 sha256 做幂等键。分批失败后重试时，前面成功的批次会回
`duplicate:true`，不会重复建会话；`counts` 累加的是后端返回的真实数字。

**归属**（照 `web/back/docs/03-登录与身份.md`）：

* 已登录 → `conversations.user_id = 账号`，换设备登录也看得见；
* 访客 → 只挂这台设备（`device_id`、`user_id IS NULL`）；之后在**这台设备**登录时，
  后端 `_attach_device` 会把它们一并收编（`adopted_conversations`），不会"导到临时设备
  后登录就看不见"；
* 所以在账号里看到数据的前提是：要么迁移时已登录，要么之后在这台设备登录一次。

### 5.6 标记与"不重复导"

```json
// localStorage['bakerai.legacy-migrated.v1']
{
  "batchId": "imp-3",
  "batchIds": ["imp-1", "imp-2", "imp-3"],
  "at": 1763000000000,
  "counts": { "cards": 3, "conversations": 4, "messages": 812, "images": 37, "skipped": 2 }
}
```

* 只在**全部批次成功**后写；写失败（隐私模式）不影响迁移本身，下次可能再传一遍，
  后端按包哈希去重。
* 这是**新 key**，老站不认识、也不会读；老 key 一个都没动。
* 清本地缓存 / 换浏览器会丢标记（也会丢老数据），此时检测不到数据，不会误报。

### 5.7 失败 → 人话（`describeMigrationError`）

| 情况 | 提示与下一步 |
|---|---|
| 单条记录本身就 >64MB（超大图） | 自动分批也装不下 → 给了两条可行路径：①「数据管理 → 导出数据」生成 ZIP 再「导入数据」；② 在数据管理里清理特别大的图后点「重试」 |
| 整包 >64MB | **不报错**，自动分批上传；界面显示"第 2/3 批" |
| 413 | 同 `too_large`（理论上分批后不会出现，兜底文案仍给导出/导入路径） |
| 网络失败 | 检查网络 → 重试；本地数据未改动 |
| 401 / 403 | 刷新页面重试；仍失败去「设置 → 账号」检查登录 |
| 400 `bad_package` | 先「先备份一份」，再用「数据管理 → 导出数据」+「导入数据」走文件路径 |
| 429 | 等一分钟重试 |
| 507 | 服务器存储满，过会儿再试 |
| 5xx | 稍后重试；反复失败反馈开发者 |
| 分批中途失败 | 额外提示"已成功 N/M 批；重试会从第 N+1 批继续（前面的批次服务器按内容去重）" |
| 已登录/访客归属 | 条上直接写"会挂到账号「X」名下" / "先挂这台设备，之后登录自动并入账号" |

### 5.8 覆盖部署的善后：Service Worker / 缓存

* 老源码（`web31/src`、`v322kit/src`）全库搜不到 `serviceWorker` / `registerSW` /
  `workbox` —— **线上版本没有注册 SW**。
* 但仍可能有过更早的部署装过。覆盖部署后，旧 SW 会继续用缓存里的旧 `index.html`，
  表现成"更新了但界面没变、数据也读不到"。
* 新前端挂载时调 `cleanupLegacyServiceWorkersOnce()`：
  `navigator.serviceWorker.getRegistrations()` 全部 `unregister()` + `caches.keys()`
  全部 `caches.delete()`；只做一次（标记 `bakerai.legacy-sw-cleaned.v1`），
  将来新站自己上 SW 不会被反复清掉。
* 注销 SW / 清缓存**不影响 IndexedDB 与 localStorage**。

## 6. 数据丢失风险清单（必须知道的"迁不过去"）

> 原则：**丢显示偏好可以，丢聊天记录不行**。下面按影响排序。

| # | 项 | 会怎样 | 为什么 / 缓解 |
|---|---|---|---|
| 1 | `contextHistory` 与屏上消息冲突 | 屏上消息为准，AI 记忆那份被丢弃并计数（后端 `notes` 会写"X 条 AI 上下文历史没有迁移"） | 新后端只有一套消息。屏上是用户认的记录；记忆可以从消息重建，反过来不行。**屏上为空时反而用 contextHistory 兜底**，不会整段丢 |
| 2 | `contextHistory` 里的 `【对话总结】` 条目 | 屏上消息非空时不进新库；屏上为空时作为一条消息进库（保留记忆） | 总结是派生内容；老消息仍在屏上消息里，服务端会重新压缩。**内容不丢，只是不再以"总结"形态存在** |
| 3 | 消息时间 | 导入的消息 `created_at` = 导入时刻，只有 `seq` 顺序 | 老库**本来就没有**消息时间戳（只有数组顺序）→ 不算丢失，但时间线看起来全是"刚导入" |
| 4 | 角色名在 `characters` 表里查不到 | 会话照样建、消息一条不少；`character_id = NULL`，标题用老名字；没有那个人的人设 | 后端 `notes` 点名哪几个角色。**丢人设是小事，丢历史是大事** |
| 5 | 群聊自动再导一次 | 新前端群聊中间层第一次进群时会用本地历史再导一条群会话 → 服务端多一份同成员的会话（内容重复） | 群聊中间层的既有行为（`seedHistory`），不是本迁移器引入的；**消息不丢，只是服务端多一份**。等列表改服务端驱动后要一并收敛（见 §8） |
| 6 | 一个角色多段存档 | 每段存档各建一条会话（消息都在）；新前端发消息时按"消息最多"的那条绑定上下文 | 新前端"一个角色 = 一条服务端会话"的既有取舍。数据不丢，但当前聊的那段不一定是绑定的那段 |
| 7 | 合并歧义 | 用户若在"旧快照"和"分片"之间删过/重排过子对话，合并可能把某段**追加**成新段 → 服务端多一段，消息不丢 | 合并器只做保守匹配（名字 + 消息交集）；匹配不上一律追加，绝不覆盖 |
| 8 | 图片格式 | 只认 png/jpeg/webp/gif 的 dataURL；avif/heic/bmp/svg 或 ZIP 内路径 → 图丢、文字保留（无字时留 `[图片]`） | 后端 `images.py` 只落这四种；写坏图比少张图更糟 |
| 9 | 单张图 >20MB | 后端丢弃该图（`MAX_IMAGE_BYTES`），消息文字仍在 | 同上；这是后端阈值，前端不重复实现 |
| 10 | 单条记录 >64MB | 自动分批也装不下（一条消息里塞了几十 MB 图）→ 明确提示导出 ZIP / 清理大图 | 浏览器的单条消息没有拆分语义；硬拆会把一条消息撕成几条 |
| 11 | `isError` 失败气泡 | 丢弃（本来就不是聊天记录） | 老持久化层写库前也会过滤；数量在摘要里报"本地另跳过 N 条失败气泡" |
| 12 | 空消息 | 丢弃 | 没字没图，迁进去只会让会话出现空气泡 |
| 13 | `myGender` | 不迁移 | 新后端没有这个状态；只写进批次报告 |
| 14 | `settings` 快照（API 配置 / 开关 / 总结配置） | 不迁移 | 新客户端不该沿用旧客户端的 API 地址与开关 |
| 15 | `order` / `cardActivity` / `subActivity` / `stripVariant` | 不迁移 | 纯列表排序 / UI 偏好；新列表马上改服务端驱动 |
| 16 | `usage`（用量统计） | 不迁移 | 本机统计，不是聊天数据 |
| 17 | `suggestions` / `sessionOutputTokens` / `promptTokens` / `lastPromptTokens` / `summaryAnchor` / `compactedBefore` | 不迁移 | 一次性缓存 / 老前端账本；新后端自己算 |
| 18 | `speakerAvatar` / `imageW/H` / `regenerateUserId` / `groupRunning` / `groupTopic` / `assignTarget` / `groupSessionId` | 不迁移 | 显示层 / 运行时字段，新后端没有对应列；`assignTarget` 新前端每次按群成员重建 |
| 19 | 跨 origin / 跨浏览器 | **读不到**（浏览器隔离），检测不到数据 | 只能在新站覆盖的**同一个 origin** 上读；否则走"导出文件 → 导入数据"。换浏览器/换设备同理 |
| 20 | 无痕模式 / 清过站点数据 | 数据可能已经不在，读不到 | 迁移前提示用户「先备份一份」；备份文件在用户手里 |
| 21 | 访客迁移后从不在这台设备登录 | 数据只在设备名下，别的设备看不到 | 文案已说明；在这台设备登录一次即自动并入账号 |
| 22 | localStorage 不可写（隐私模式） | 迁移成功但标记写不进 → 下次可能再传 | 后端按包哈希去重，不会重复建会话；界面会提示"这次没记下迁移标记"？→ 目前只在日志里，不影响数据 |

## 7. 覆盖部署 checklist（同 origin 覆盖老 web）

> 用户口径：**新 web 直接覆盖原 web（同一个 origin）**。下面是上线/回滚都必须做的。

### 7.1 上线前

1. **确认 origin 对得上**
   * 线上老站在 `chat.peilika.beer`（vhost `peilika-chat` → `/var/www/peilika-chat`，
     web31/3.1 线）。
   * `test2.peilika.beer`（`peilika-v2` → `/var/www/peilika-v2`，3.2.2 线）是另一套
     origin；如果也要覆盖，**分别部署**。任何跨 origin 的"搬家"都读不到老 IndexedDB。
   * 不要用"路径前缀"换站（`/new/`）：IndexedDB 按 origin 隔离，同 origin 同路径无所谓，
     但同 origin 不同**域名/子域**就是两个站。
2. **备份老站文件**（不要只 `rm -rf`）：
   ```bash
   tar -czf /root/peilika-chat_$(date +%Y%m%d-%H%M).tgz -C /var/www peilika-chat
   cp /etc/nginx/conf.d/<vhost>.conf /root/<vhost>.conf.$(date +%Y%m%d-%H%M).bak
   ```
   3.2.2 那边同理备份 `/var/www/peilika-v2`。
3. **确认老站没有 SW**（本次已核对源码：没有注册）。若线上实测有（浏览器
   DevTools → Application → Service Workers），记下来；新站启动会自动注销 + 清缓存。
4. **记录迁移标记 key**：`bakerai.legacy-migrated.v1`（新 key）。
   不要复用它做别的事；不要清它（清了只会让用户再看到一次迁移提示，不会重复导）。

### 7.2 部署

1. `npm run build` → 把 `dist/` 同步到 `/var/www/peilika-chat`（保留目录权限）。
2. 确认反代/后端地址：生产建议**同源**，`/v1` 反代到新后端；若不同源，构建时
   `VITE_BAKER_BACKEND` 或 `localStorage['baker_backend_url']` 指定。
3. 打开站点，确认：
   * 顶部出现迁移条，数字与老站"数据管理"里的统计对得上；
   * 点「先备份一份」能下载 JSON；
   * 点「立即迁移」→ 进度 → 摘要；`GET /v1/conversations`（带同一设备 token）能看到会话；
   * 刷新后迁移条不再出现（标记已写）。

### 7.3 回滚

1. 把备份的 `peilika-chat` 解回原目录（或换回旧 dist）。
2. **不需要恢复任何用户数据**：老 IndexedDB / localStorage key 一个都没被删改；
   新站只往服务端写了一份，并写了一个新 key 的标记。
3. 若用户在新站已经继续聊过：那些消息在**新后端**里；老站本地没有。回滚前先让用户
   在新站「数据管理 → 导出数据」留一份。
4. 迁移标记 `bakerai.legacy-migrated.v1` 留着不碍事；老站不读它。

### 7.4 上线后观察

* `notes` 里"未收录角色"的名单（决定要不要补角色表）；

## 8. 将来"列表改服务端驱动"后，本地老存档怎么处理

> 另一条线的设计是：卡片/会话列表改由服务端 `/v1/conversations` 驱动，
> 本地存档退化为缓存。本迁移器不依赖列表怎么渲染，但要把边界写清楚。

建议（也是本实现的默认行为）：

1. **本地老存档原样保留**（IndexedDB 一个键都不删），只把"已迁移"记在
   `bakerai.legacy-migrated.v1` 里。
2. **列表不显示本地老存档**（服务端会话才是列表真相）；本地老存档只在
   "离线 / 服务端不可用"时作为只读兜底，或干脆不展示。
3. **绝不自动清理**。将来若要释放空间，只能由用户显式点「清理本地旧存档」并二次确认；
   清理前必须保证：迁移标记存在 + 服务端会话数 ≥ 本地统计（或用户明确接受）。
4. 迁移标记**不要**被"清空会话/退出登录/换账号"顺手清掉 —— 它记录的是"这台浏览器
   的旧数据已经搬过一次"，与账号无关。
5. 新前端继续写 `cards`（现有持久化层）也没关系：迁移器读的是"分片 ∪ 旧快照"的并集，
   旧快照被新数据覆盖只会让并集更完整，不会丢。
