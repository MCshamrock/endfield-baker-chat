## 1. 设备注册 500：`os_ver` 超过列宽（实测抓到）

**现象**：网页一打开就报 `/v1/auth/device 500`，账号页永远停在"正在连接服务器…"。

**根因**：`apiClient.deviceInfo()` 把整条 User-Agent（130+ 字符）塞进 `os_ver`，
后端 `devices.os_ver` 是 `VARCHAR(32)`，MySQL 抛 `Data too long` → 未捕获异常 → 500。

**修法**：`apiClient.ts`

- `os_ver` 只写短名字（`Windows 10/11` / `Android 14` / `iOS 17.x` / `macOS` / `Linux`）；
- 所有字段按后端列宽截断（`platform 32 / app_ver 32 / os_ver 32 / tz 64 / locale 16`）。

**验证**：无头 Edge 打开页面，`/v1/auth/device` 由 500 变 201，console 0 错误；
`scripts/contract-smoke.mjs` 与 `adapter-e2e.mjs` 全部通过。

> 后端侧建议：`devices.os_ver` 放宽到 `VARCHAR(255)`（或入口统一截断），
> 这样别的老客户端塞长 UA 也不会 500。见 05 §4。

## 2. 群聊错误体两种形状：`[object Object]` 与会话过期识别

**现象**：群聊失败时提示 `群聊生成失败：[object Object]`；会话过期（300s）后不自动重建。

**根因**：`groupBackend.postJson` 只认**扁平**错误体（`{error:"…", code, session_expired}`），
而新后端的统一错误出口是 `{error:{code,message,details}}`。`json.error` 取到对象后
被当成字符串拼进提示；`session_expired` 也读不到。

**修法**：`groupBackend.ts` 的 `postJson` 同时解析两种形状：

- 字符串 `error` → 直接当文案；
- 对象 `error` → 取 `error.message` / `error.code` / `error.details.retry_after`；
- `session_expired` 的判据：顶层 `session_expired === true`，或 code 是
  `session_expired` / `no_conversation`。

**验证**：`useGroupChat` 的自动重建路径依赖这个布尔值；类型检查通过，
群聊协议本身由后端 doc 13（第 7–11 条）验过。

## 3. 后端地址硬编码在旧网关

**现象**：原前端写死 `https://api.peilika.beer/chat`、`…/group`（正式/备用两个域名）。

**修法**：`constants/apiRoutes.ts` 重写为"一个后端根地址"：

- 解析顺序：`localStorage['baker_backend_url']` → `VITE_BAKER_BACKEND` →
  `file://` 回退 `127.0.0.1:5660` → 同源；
- 自动剥掉粘错的 `/v1`、`/chat`、`/group`、末尾斜杠；
- 保留 `API_BASES` / `API_ROUTE_LABELS` / `currentApiRoute` / `gatewayUrl` / `groupBaseUrl`
  这些旧导出（设置界面还在用），但两个"路线"现在指向同一个地址。

**验证**：`npm run dev` 下页面相对路径请求经 vite 代理打到 5660，设备注册 201；
`npm run build` 产物同源部署时相对路径直接可用。

## 4. 流式失败回退会把同一句话写两遍

**现象**（理论上）：SSE 建立失败 → 回退非流式 → 服务端两条一样的用户消息。

**根因**：两次调用各自生成 `client_msg_id`。

**修法**：`backend.ts` 的 `pendingTurns`

- key = `conversationId|history.length|text[0:80]`；
- 同一轮内的重试、流式回退都复用同一个 id；
- 成功后清掉 key（同一句话再说一次是新消息）。

**验证**：`adapter-e2e.mjs` §3/§4 —— 第二句用新键、同一句重复内容用新键；
后端幂等由 `contract-smoke.mjs` §7 覆盖（`duplicate=true`）。

## 5. `duplicate=true` 时没有回复

**现象**（理论上）：请求其实成功了，但响应丢在网络上 → 重发得到 `{duplicate:true, reply:null}`
→ 界面收到空回复。

**修法**：

1. 用 `GET /messages?after_seq={seq}` 把已存的助手回复捞回来；
2. 捞不到 → `POST /continue` 补一条；
3. 还不行 → 明确报"消息已保存，但生成失败"。

**验证**：`adapter-e2e.mjs` 里由假 fetch 模拟正常路径；幂等分支由
`contract-smoke.mjs` 的第 7 节确认真实后端会返回 `duplicate=true`。

## 6. 新会话 `next_seq` 是 0，不是 1

**现象**：`ensureConversation` 里"空会话"判定写成 `next_seq <= 1`，
会把**只有一条消息**的服务端会话误判为空并删掉。

**修法**：改成 `(next_seq ?? 0) === 0`；排序按 `next_seq` 降序仍保留。

**验证**：`contract-smoke.mjs` 断言新建会话 `next_seq === 0`；
`adapter-e2e.mjs` 验证导入了 4 条消息的会话不会被二次导入/删除。

## 7. 登出 / 服务端重置后会话 404

**现象**：换账号或服务端库重置后，本地还记着旧会话 id，发消息 404 `no_conversation`。

**修法**：`sendTurn` 捕获 `no_conversation` → `dropBinding()` →
用同一份 `seed` 重新走"找/导入/新建"→ 用**新**幂等键重发一次。

**验证**：代码路径由类型检查 + 逻辑审阅覆盖；真实 404 场景需要重置服务端库，
未做破坏性测试（见 04 §5 的说明）。

## 8. 历史导入：助手回复不能丢

**现象**（设计风险）：最初打算逐条 `POST /messages` 导入历史，
但后端那个端点只写 `side='user'`，助手回复会全部丢失。

**修法**：改用 `POST /v1/imports`（老的 JSON 数据包形状），两种 side、说话人、
图片都能进；导入前删除同角色的空会话，避免列表里多一条空壳。

**验证**：`adapter-e2e.mjs` §2 —— 服务端会话里 user 与 assistant 两侧都在，且只绑定一条会话。

## 9. 设置里"后端路线"文案与新现实不符

## 10. 文档 13 提到的"流式多弹一条空回复"

**结论：这份代码里不存在，无需修。**

`web/back/docs/13-本地联调清单.md` §3.1 记录的问题（`onUnplayable` 检查了还没赋值的

fullText = result.reply          // 先赋值

## 11. 群聊整条链路迁到 /v1（旧版是独立服务）

**现象**：旧中间层把群聊打到 `api.peilika.beer/group`（独立服务 :5810），
新后端虽然兼容这套协议，但它不是"新架构"（调度状态在内存、300s 回收、
历史每轮全量上传）。

**修法**：`groupBackend.ts` 重写为 `/v1`：

- 建群 `POST /conversations`（members=slug、speak_mode、player_role）；
- 玩家说话 `POST /messages`；下一位 `POST /next`；
- `round` / `weighted` 在中间层里循环 `/next` 直到 `done`，一次性把这一轮返回；
- 第一次拿到历史时用 `/imports` 导入（说话人保留），用别名表把 id 换掉；
- 关群 `DELETE /conversations`。

**验证**：`scripts/group-e2e.mjs` 24/24（建群/导入/三人一轮/assign/权重）。

## 12. 群聊「加权模式」+ 建群后的「发言权重」弹窗

**需求**：新后端的主路径是 `weighted`（按 active 权重加权随机）——权重不暴露给
玩家，这个算法等于没法调。

**修法**：

- `GroupSpeakMode` 增加 `'weighted'`；`GROUP_SPEAK_MODES` 变四项（创建/设置弹窗
  改成 2×2 网格，一行四个会挤成三行字）；
- 新建群默认 `weighted`（旧群保持原设置）；
- 建群成功后弹 `GroupWeightsDialog`：每个成员一条滑杆（1–100），保存时
  `PUT /characters/{slug}/weight`；群设置里也留了「调整发言权重…」入口。

**验证**：`group-e2e.mjs` §5；无头浏览器实跑「建群 → 权重弹窗 3 行」通过，
截图见 `docs/assets/group-weights.png`。

## 13. 后端导入器不认 `weighted`（1 行补丁）

**现象**：`app/imports/normalize.py` 的 `SPEAK_MODES` 只有三种；一份
`speakMode: "weighted"` 的群聊被导入后会被**悄悄降级成 smart**，玩家的权重设置白设。

**修法**：`SPEAK_MODES = ("round", "smart", "assign", "weighted")`（与
`ConversationCreateRequest` 的 pattern 对齐）。这是本次唯一一处后端改动，属于
"导入器没跟上自己的新枚举"。

**验证**：重启后端后，导入一份 weighted 群聊再查 `GET /v1/conversations`，
`speak_mode` 仍是 `weighted`（实测命令见 04 §3）。
