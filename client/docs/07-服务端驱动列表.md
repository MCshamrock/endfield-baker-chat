## 0. 范围与不做什么

| 做 | 不做（本轮/本设计） |
|---|---|
| 列表数据源从 `chatStore.cards` 换成 `GET /v1/conversations` | 不重写聊天区视觉与排版（`ChatArea` / `useChatRows` 逻辑保留） |
| 登录 / 领取 / 迁移后，服务端会话**立刻出现在列表里** | 不做多端实时同步（WebSocket / SSE 推送列表变化） |
| 子卡 ↔ 服务端会话 **1:1**（按会话 id，而不是按角色） | 不做离线编辑队列（断网只读缓存，不排队发送） |
| 本地存档降级为**可丢缓存** | 不删 `fe-migrate` 的老数据读取逻辑（见 §5） |

> 关键判断：现在的 `baker_v1_bindings`（角色 → 会话）会在 P1 里**退役**。
> 它原本是为了"界面拿不到会话 id"而做的妥协（见 `docs/05 §2`）。
> 服务端驱动之后，会话 id 直接挂在子卡上，绑定表只留读取兼容。

### 1.3 本地存档和 `/v1` 会话现在怎么对上

`ensureConversation()`（`backend.ts:545`）在**第一次给某个角色发消息**时按顺序找会话：

1. `baker_v1_bindings[角色 slug]` 有 → 直接用（`backend.ts:375`）；
2. 没有 → `GET /v1/conversations`（`backend.ts:441`），过滤 `mode==='single' && character_id===slug`，按 `next_seq` 取最大；
3. 找到的会话是空的（`next_seq===0`）且本地有历史 → 删掉它改走导入（`backend.ts:492`，`POST /v1/imports`，包哈希幂等）；
4. 还是没有 → `POST /v1/conversations` 新建（`backend.ts:459`）；
5. 找到/新建的结果写回绑定表（`backend.ts:573-576`）。

群聊走另一套：`baker_v1_group_alias`（`groupBackend.ts:114`）把"界面里的旧 id"映射到"导入后新建的服务端 id"，解析函数 `resolveGroupSessionId()`（`groupBackend.ts:165`）。

**由此产生的已知缺陷**（就是这次要还的债）：

- 绑定键是**角色**，不是会话：同一角色开两段存档会共用一条服务端会话（`docs/05 §2`）；
- 服务器上已有的会话，界面**不知道它存在**，只有"点进那个角色"才会被发现（`docs/05 §3`）——所以领取/迁移之后列表还是空的；
- 清浏览器数据/换设备，列表直接空掉（列表是本地真相）；
- 本地"最后一条消息"只反映这台设备看到的东西，不反映账号真实状态。

## 2. 目标数据流

### 2.1 一张图

```
                      ┌──────────────────────────── 启动 / 登录 / 领取 / 迁移完成
                      ▼
      GET /v1/characters ──► 角色目录（slug/name/attribute/weight）
                      │        └─ 本地 CHARACTERS 只补：头像 / 性别 / 文案（按 name 对齐）
                      ▼
      GET /v1/conversations ──► 会话列表（single/group、标题、成员、next_seq、last_active_at）
                      │        └─ 前端组装成"卡 → 子卡"树（子卡.remoteId = 会话 id）
                      ▼
      ┌────────────── 渲染（只读服务端快照）──────────────┐
      │  单聊卡：一个角色一张卡，卡下每个服务端会话一张子卡   │
      │  群聊卡：mode=group，成员叠层 + 标题 + 末条预览       │
      └───────────────────────────────────────────────────┘
                      │ 点开某张子卡
                      ▼
      GET /v1/conversations/{id}/messages?after_seq=…&limit=… ──► 填进本地缓存（渲染用）
                      │
                      ▼
      发送：POST …/messages 或 …/messages:stream（乐观显示 → 用返回的 seq 落定）
      群聊：POST …/next（本轮下一位）、…/continue（继续说）、…/suggestions
```

### 2.2 逐条说明

**① 角色目录 `GET /v1/characters`**

- 用途：决定"有哪些干员"、slug↔名字、属性、群聊默认权重。
- 本地那份 36 张卡：**只留头像 / 性别 / 文案**（`src/constants/character.ts:119`），按 `name` 与
  服务端对齐；服务端新增角色若本地没有图 → 用默认头像占位（`DEFAULT_AVATAR_URL`）。
- 服务端 `avatar` 目前是空串（`schema/002_seed.sql:11` 起），所以**头像继续用本地资源**，
  不把图片搬到服务端（也让 CSP 的 `img-src 'self'` 不用改）。

**② 会话列表 `GET /v1/conversations`**

- 现有字段够画"卡 + 子卡 + 群成员"：`id / character_id(slug) / mode / title / members / next_seq / created_at / last_active_at`（`schemas.py:155-167`）。
- **没有** `last_message` 与 `message_count` → 现在要显示"末条预览"只有两条路：
  - N+1：每个会话再 `GET …/messages?limit=1`（`limit` 最小 1 合法，但 `after_seq` 要传 `next_seq-1`）→ 50 个会话 = 51 次请求，**不可接受**；
  - 让后端在列表里带 `last_message {text, side, speaker, created_at}` + `message_count` → **见 §6 的 P0 需求**。
- 前端组装规则：
  - `mode='single'` → 按 `character_id` 归到那张卡下；一个角色有 N 条服务端会话 → **N 张子卡**（终于和 `docs/05 §2` 的限制说再见）；
  - `mode='group'` → 群聊模式的卡，成员来自 `members`（目前是**名字**，本地按名字配头像即可，`repos/conversations.py:190`）；
  - 卡/子卡排序：`last_active_at` 倒序（服务端已经排好，前端不再自己算 `cardActiveAt`）。
- 空角色（服务端没有会话）：保留本地"占位卡"（点进去发第一句话时才 `POST /conversations`），
  与今天的体验一致；**占位卡不算真相**，只是入口。

**③ 会话内容 `GET /v1/conversations/{id}/messages`**

- 首屏只要最近 N 条（建议 N=50）：`after_seq = max(0, next_seq - 1 - N)`，`limit = N`（`seq` 从 1 开始，`next_seq-1` 才是最后一条）。
  ⚠️ 这依赖 `seq` 连续；若将来支持删消息出现空洞，需要后端加 `tail=1` 或 `before_seq`（§6）。
- 增量同步（拿到更新的消息）用返回的 `next_after_seq` 接着拉；**往上翻更早的历史**需要后端支持 `before_seq`（§6），P1 先只显示最近 N 条，翻页放 P2。
- 拉回来的消息写进本地缓存（`conversations[i].messages`），**渲染管线完全不用改**（`useChatRows` 只看 `messages`）。
- 消息里的图片：`MessageOut` 给的是 `attachment_id` + `attachment_url`（`schemas.py:291`），
  本地气泡要 `dataURL`；P1 先按 `[图片]` 占位（与历史导入的处理一致，`backend.ts:492` 同口径），
  真正取图放 P2（走 `attachment_url` + 设备 token）。

**④ 发送 `POST /conversations/{id}/messages` / `messages:stream`**

- P2 起：本地消息数组只做**乐观显示**；服务端返回 `seq/reply_seq` 后把本地消息的
  `remoteSeq` 落定（`ChatMessage` 加可选字段，不进导出）。
- 幂等键沿用现在的 `client_msg_id`（`docs/01 §5`）；`duplicate=true` 的补救逻辑（拉回回复 / `continue`）
  已经在 `backend.ts:737` 附近，保留。
- 流式：现有的 SSE 帧映射（`backend.ts:1025`）不变，只是"会话来源"从绑定表变成子卡上的 `remoteId`。

**⑤ 群聊**

- 列表：`mode='group'` 的会话直接成为群聊卡（标题、成员、`speak_mode`）。
- **群名口径要统一**：服务端默认标题是成员名用「、」拼（`api/conversations.py:116`），
  而前端今天显示的是「A、B和C的群聊」（`chat.ts:167` 的 `groupTitle()`）。
  建议：**有服务端 `title` 就用它**（将来支持自定义群名），标题为空时才用本地规则拼。
- 发言：`/messages`（玩家说）→ `/next`（下一位，`done=true` 收尾）→ `/continue`（补一条）→ `/suggestions`（推荐）。
  现有 `requestGroupReply()`（`groupBackend.ts:565`）已经是这套逻辑，P3 只需把"会话 id 从哪来"换掉。
- 缺失字段：`player_role`（我的身份）建群时写入、**列表不返回**（`schemas.py:155` 没有这个字段，`models/chat.py:47` 有列）→ §6。
- 切模式 / 改成员 / 改群名：现在**没有 PATCH**，前端只能"作废会话重建"（`chat.ts:740/754`）。
  服务端驱动后重建会在列表里堆垃圾 → §6 需要 `PATCH`。

### 2.3 缓存与离线（弱网）

| 状态 | 表现 |
|---|---|
| 在线 | 列表/消息以服务端为准；本地缓存顺手写（不阻塞 UI） |
| 弱网（请求慢） | 先渲染缓存（有就画），顶部细条"正在同步…"；不要白屏 |
| 断网 | 列表 + 已看过的会话可读（缓存），**发送按钮禁用** + 一句"离线：只能看缓存，联网后才能发" |
| 缓存过期 | 进入会话时静默拉增量；拉失败保留缓存并标"未同步" |
| 切换账号 / 登出 | **清空会话缓存与列表**（否则数据串号）；角色目录与偏好不清 |

缓存放哪：继续用 IndexedDB（`useChatPersistence`），但键与结构改成"按账号/设备分桶"，
例如 `cardsCache:<ownerKey>`，`ownerKey = user:<id>` 或 `device:<id>`（避免换账号读到别人的缓存）。

### 2.4 列表 = 角色目录 × 会话

```
卡片（单聊）   = 一个角色（来自 /v1/characters）+ 本地头像/性别
  子卡 1..N   = 这个角色的服务端会话，按 last_active_at 倒序
卡片（群聊）   = 一个 mode='group' 的会话（成员来自 members）
空角色卡       = 本地占位（没有服务端会话）：点进去发第一句才 POST /conversations
```

## 4. 三期计划（每期独立可跑、独立验收）

### P1 · 列表只读服务端 + 点进去看历史（先解决"领了看不见"）—— ✅ 已完成 2026-11-18

**范围**
- 新 `utils/conversationSync.ts` + `stores/list.ts`：拉 `GET /v1/conversations`，映射成卡树。
- `chatStore` 加 `applyServerList()`；子卡带 `remoteId`；`ensureConversation` 改成"有 `remoteId` 直接用"。
- 点开子卡：`GET /v1/conversations/{id}/messages?after_seq=next_seq-1-N&limit=50` 填消息缓存。
- 领取成功 / 注册带码成功 / 登录成功 / 启动 → `listStore.refresh()`。
- 保留"空角色占位卡"（发第一句才建会话）。
- 发送仍是今天的路径（`backend.ts` 发消息），只是会话 id 来源变了 —— 保证 P1 就能继续聊天。

**验收判据**
- 用户：新设备注册时填取件码 → 注册成功 → **左侧列表立刻出现领取到的会话**（标题/末条/时间），点进去能看到历史并继续聊。
- 用户：换设备登录同一账号 → 列表与上一台一致；清掉浏览器数据重新登录 → 列表还在。
- 自动化：`node scripts/list-e2e.mjs`（假后端）
  1. 列表 200 两条（1 单聊 + 1 群聊）→ 组装出 1 张单聊卡 + 1 张群聊卡；
  2. `character_id` 映射到角色名/头像；
  3. 子卡 `remoteId` 等于服务端 id；
  4. 选中 → 拉消息（断言 `after_seq`、分页到 `next_after_seq` 收敛）；
  5. 领取 → `refresh()` 后列表多一条（这条就是本次要兑现的用户诉求）；
  6. 断网（fetch 抛错）→ 列表保留缓存 + `offline=true`，不抛异常。
- 回归：`npm run build` 0 错；`contract-smoke` / `adapter-e2e` / `group-e2e` / `claim-smoke` 全绿。

### P2 · 发送/流式/重生成接服务端，本地退化为缓存

**范围**
- 发送成功以服务端 `seq` 为准；本地消息加 `remoteSeq`；流式帧照旧。
- 重生成 / 续写 / 推荐：按 `remoteId` 走。
- 刷新/切会话时增量对账（本地最后 seq vs `next_seq`）。
- 导出/导入语义重定义（建议：导出 = 服务端数据快照；导入继续走 `POST /v1/imports`）。
- 图片：`attachment_url` 取图（带 token），缓存到 IndexedDB。

**验收判据**
- 用户：两台设备交替发言，另一台刷新后能看到对方消息（不要求实时）。
- 用户：断网发送 → 明确失败提示（不发出去、不留幽灵气泡）。
- 自动化：`scripts/send-e2e.mjs` 断言"乐观消息 → seq 落定 / duplicate 补救 / 流式帧映射 / 429 退避"。
- 回归：以上四个脚本全绿 + 群聊 24 项。

### P3 · 群聊服务端驱动 + 旧数据迁移合流

**范围**
- 群聊卡 = `mode='group'` 会话；`baker_v1_group_alias` / `baker_v1_groups` 退役。
- 切模式/改成员/改名：有 `PATCH` 就改，没有就"新建并提示"（§6）。
- 旧本地数据：由 fe-migrate 导入服务端后，列表只显示服务端 → 本地存档标记已迁移，
  不再参与列表（§5）。
- 导出老存档的能力保留（迁移失败时的救生圈）。

**验收判据**
- 用户：老用户升级后，原有群聊以服务端会话出现；发言/下一句正常。
- 自动化：`scripts/group-list-e2e.mjs`；迁移前后条数对账（本地 N 段 → 服务端 N 条 + 0 丢失）。

### 灰度与回滚

新增一个开关（localStorage `baker_list_source = 'local' | 'server'`）：
**默认值按这台设备有没有旧数据决定** —— 没有旧数据（新设备/新账号）默认 `server`；
有旧数据默认 `local`，且必须先迁移（`bakerai.legacy-migrated.v1`）才允许切 `server`。
被门槛拒绝时**不写 localStorage**（先判定后写入）。

**用户显式选择优先**（审计 D5 后补）：设置页点选会写
`baker_list_source_user_set=1`；之后登录 / 领取触发的自动切换**不再改**用户的选择，
只有"从没显式选过"的设备才会自动挑服务端列表。

- `local`：完全按今天的行为跑（绑定表 + 本地卡）；
- `server`：走新链路（P1 的 `applyServerList`）。

好处：P1 上线即可灰度；出问题一键切回；fe-migrate 的老逻辑也不必立刻删。

### 与总结/压缩清理的先后（2026-11-18 追加，替代原「移植 3.1 智能总结」）

**结论：P1（列表服务端化）先上；前端"死总结路径"的清理放 P1 之后。**

三条理由：

1. **改的东西不重叠，但会撞在同一条执行链上**：P1 改"列表/会话从哪来"，清理改"历史怎么压"
   （`useAiChat` 的请求前判定、`chat.ts` 的裁剪状态机）。两者都会动一轮请求的前后逻辑，
   混在一个 PR 里出问题无法归因 —— 是列表选错会话，还是清理把历史裁了？
2. **清理的验收依赖 P1 的真相**：清掉前端假总结之后，要看"服务端压缩确实在跑、
   前端没有插一脚"。没有 P1 的服务端列表/消息，连"这条会话服务端有什么历史"都对不上。
3. **原计划的"3.1 智能总结移植"已撤销**：新后端 `memory.compress_to_fit` 自己做压缩/总结
   （`app/generate.py:276/583`、`app/settings.py:127-144`），前端搬过来只会形成第二条压缩链。
   前端要做的是**减法**，清单见 [`08-总结与压缩归属.md`](08-总结与压缩归属.md)。

**执行顺序**：P1 合并 → 跑 `docs/08 §4` 的 A/B 两条闸门（一个小 PR，只按 `apiMode` 分支）→ 再 P2。

**清理后的判据**：`adapter-e2e` 抓请求体断言**没有** `need_summary`；
群聊 > 50 条发消息时网络面板**没有** `/api/legacy-key`；长历史对话不再出现"总结失败，已跳过"。

## 5. 与 `fe-migrate` 的边界

> 写这一节时（2026-11-18 00:35 之后）fe-migrate 的文件已经落地，按**实际 API** 对齐：

**fe-migrate 已有的公开能力（我只调用，不改）**

| 能力 | 位置 |
|---|---|
| 检测有没有老数据 / 读老数据 | `detectLegacyLocal()` / `readLegacyLocal()`（`legacyLocalData.ts:315/347`） |
| 打包成导入包（JSON / Blob） | `toImportPackageJson()` / `toImportPackage()`（`:364/369`） |
| 执行迁移（`POST /v1/imports`） | `migrateLegacyLocal({onProgress, force})`（`:402`） |

| 备份下载 / 老 SW 清理 | `downloadLegacyBackup()` / `cleanupLegacyServiceWorkersOnce()`（`:469/516`） |
| 迁移标记的存储键 | `bakerai.legacy-migrated.v1`（`legacyLocalCore.ts:52`） |

**文件所有权（约定）**

| 文件 | 归属 | 说明 |
|---|---|---|
| `src/utils/legacyLocalData.ts` / `legacyLocalCore.ts` | **fe-migrate 独占** | 我只调用上表的公开函数，**不修改、不删除** |
| `src/components/layout/LegacyMigrateBanner.vue` | **fe-migrate 独占** | 迁移入口 UI 归它；我不动 |
| `src/utils/importMerge.ts` / `zipExport.ts` 的"读老包"部分 | fe-migrate | 我不动解析逻辑 |
| `src/utils/conversationSync.ts` / `src/stores/list.ts`（我新建） | 我 | 新文件，零冲突 |
| `src/stores/chat.ts` | **共享，冲突高发** | 我加的 `applyServerList` / `upsertRemoteMessages` 集中在文件尾部（新函数块）；fe-migrate 若也要改 `cards` 结构，先合并一次再动 |
| `src/composables/useChatPersistence.ts` | **共享，冲突高发** | 我先不动键结构，只加"按 owner 分桶读"的可选分支；fe-migrate 的迁移读写走老 key，互不影响 |
| `src/App.vue` | **共享** | 我只加 `listStore.refresh()` 的调用点；启动清理与迁移提示条都留给 fe-migrate |

**迁移完成后列表会不会重复显示**

设计结论：

1. 迁移（fe-migrate）只负责"把老本地数据写进服务端"，**不负责列表**；
2. **不新造标记**：直接用它的 `isLegacyMigrated()`（键 `bakerai.legacy-migrated.v1`）；
3. P1 的列表**只显示服务端会话**；本地老卡不再进列表（重复问题从源头消失）；
4. 本地老存档**不删**（救生圈）：`downloadLegacyBackup()` 仍可导出一份；清空入口照旧；
5. 迁移成功后它会调 `forgetAllBindings()`（`legacyLocalData.ts:434`）——
   与我在领取后的处理一致，正好为 P1 的清绑定让路；
6. 迁移中途失败 → 标记不写，列表回退 `local` 模式（灰度开关），用户看到的就是今天的样子。

> 一句话：**重复显示不可能发生，因为列表不再读本地卡。** 唯一要防的是
> "迁移没跑完就把列表切成 server"（会看起来像数据丢了）—— 所以开关的默认值
> 必须是"`isLegacyMigrated()` 为真之后才允许切 server"。

**协作方式（减少同文件冲突）**

1. 我的改动尽量落在**新文件**（`stores/list.ts`、`utils/conversationSync.ts`、`scripts/list-e2e.mjs`）；
2. `stores/chat.ts` 里我只新增两个函数（`applyServerList` / `upsertRemoteMessages`），不改既有函数签名；
   若必须改，先告诉 fe-migrate 再动；
3. `useChatPersistence.ts` 我只加"按 owner 分桶"的可选分支，老 key 的读写一行不动；
4. `App.vue` 我只加 `listStore.refresh()` 的调用点，不碰启动清理和 `LegacyMigrateBanner`；
5. 合并顺序：**fe-migrate 先合 → 我再合**（我的改动依赖它产出的"已迁移"标记与 `forgetAllBindings` 行为）。
