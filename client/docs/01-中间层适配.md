# 中间层适配：旧前端 × 新后端

> 本文讲清"前端只发会话指针 + 新事件 + 幂等键"这件事在代码里怎么落地的。
> 对应代码：`src/utils/backend.ts`（单聊）、`src/utils/groupBackend.ts`（群聊）、
> `src/utils/apiClient.ts`（设备凭证与统一请求）。
> 后端契约以 `web/back/app/schemas.py` 与 `web/back/docs/00-设计定稿-v1.md` 为准。

---

## 1. 为什么要换：两种模型的差别

| | 旧前端（3.0–3.2.2） | 新后端 |
|---|---|---|
| 会话/消息的真相 | **客户端本地**（`localStorage`），每轮把最近 15–25 轮 `history` 整个传上去 | **服务端 MySQL**（`conversations` / `messages`） |
| 客户端发什么 | `character_id` + `message` + `history[]` + 一堆运行时开关 | 会话指针 + 新消息 + `client_msg_id` |
| 角色清单 | 前端硬编码 35 个 `CHARACTER_ID_MAP` | `GET /v1/characters`（36 个，服务端权威） |
| 压缩/预算 | 前端算 `contextWindow × 0.8` | 服务端按 20 万 token 预算压缩 |
| 图片 | base64 dataURL 塞在消息里 | `POST /v1/attachments`，消息只带 `attachment_id` |
| 幂等 | 没有 | `client_msg_id` 唯一约束 |

**界面是按旧模型写的**（`useAiChat` 只认"给 history、拿 reply"），
所以中间层必须把两种模型缝起来，而不是让界面重写。

## 2. 一轮对话发生了什么

```
useAiChat.fetchBackendReply/Stream(request)
        │  request = { character/character_id, message, history[], think, immersive_mode }
        ▼
prepareTurn()                                   ← src/utils/backend.ts
  ① apiClient.ensureDeviceToken()               POST /v1/auth/device（只在第一次）
  ② ensureConversation(role, history)           GET/POST /v1/conversations
       └─ 本地没有绑定 → 服务端找同名单聊 → 都没有就导入历史 → 再不行建空会话
  ③ 当前轮有图 → uploadImage()                  POST /v1/attachments（multipart，字段 file）
  ④ clientMsgIdFor(turnKey)                     生成/复用幂等键
        ▼
sendTurn() / SSE
  POST /v1/conversations/{id}/messages           {client_msg_id, text, attachment_id, immersive, think, local_time}
  POST /v1/conversations/{id}/messages:stream    Accept: text/event-stream（帧：delta / done / error）
        ▼
{ reply, usage }  →  useAiChat 按原逻辑分条播放
```

**关键点：`request.history` 只在第一次见到某个角色时用一次**（导入服务端），
此后每一轮都不再上传历史 —— 这是"前端适配后端"的判据。

## 3. 会话绑定（角色 → 服务端会话）

### 3.1 绑定表

`localStorage['baker_v1_bindings']`：

```json
{ "perlica": { "id": "f99dfb81…", "at": 1763400000000 } }
```

键是**角色 slug**。为什么按角色而不是按"界面里的某段子对话"：
界面里的 `Conversation` 没有稳定 id（只有数组下标 + 名字），中间层拿不到；
按角色绑定是本版能确定的最细粒度。代价见 [`05-已知差异与待办.md`](05-已知差异与待办.md) §2。

### 3.2 找会话的顺序

1. 本地绑定表里有 → 直接用；
2. 没有 → `GET /v1/conversations`，找 `mode === 'single' && character_id === slug`
   且 `next_seq` 最大的一条（`localStorage` 被清、换浏览器时靠这一步接回历史）；
3. 找到的会话是**空的**（`next_seq === 0`）且本地有历史 → 删掉它，走导入；
4. 没有可用会话 → 用 `/v1/imports` 导入历史；导入成功后再找一次；
5. 还是没有 → `POST /v1/conversations` 建一条空的。

> ⚠ 新会话的 `next_seq` 是 **0**（第一条消息才拿 `seq=1`），不是 1。
> 早期代码按 `<= 1` 判空会把"只有一条消息的会话"误删，已改成 `=== 0`。

### 3.3 历史导入（`POST /v1/imports`）

为什么不用逐条 `POST /messages`：那个端点**只能写 user 侧**
（服务端把"玩家消息"和"助手回复"分开落库），逐条写会把所有助手回复丢掉，
模型看到的上下文就只剩玩家单方面说话。

导入包用老客户端的 JSON 形状（`web/back/docs/02-数据包迁移.md` §1.2）：

```json
{
  "version": 1,
  "myGender": "male",
  "cards": [{
    "members": [],
    "conversations": [{
      "name": "佩丽卡",
      "messages": [
        { "side": "mine",  "text": "你好，佩丽卡。" },
        { "side": "other", "text": "（点头）管理员，今天的日程已经排好了。" }
      ]
    }]
  }]
}
```

规则：

- 只导入 `request.history` 里**最近 30 条**（`BACKEND_HISTORY_LIMIT`）；
- `role: 'user' → side: 'mine'`，`'assistant' → side: 'other'`；
- 前端"智能总结"的合成行（`【对话总结】` 开头）**不当成真人对话导入**；
- 历史图片不重传：正文用 `[图片]` 占位（服务端本来也不会把历史图塞进 prompt）；
- 包内容 sha256 是后端幂等键：同一个包传两次不会导两遍。

导入会**新建一条会话**，所以导入前会把同角色的空会话删掉，避免列表里多一条空壳。

### 3.4 会话失效自愈

以下情况服务端会回 `no_conversation`（404）：

- 服务端库重置 / 迁移；
- 这台设备登出账号后，之前归到账号名下的会话不可见；
- 会话被其它端删了。

处理：丢掉本地绑定 → 用 `request.history` 重新导入/新建 → 用**同一个** `client_msg_id`
重发（此时消息还没写进去，重发不会重复）。最多重试 1 次，避免死循环。

## 4. 端点映射（旧 → 新）

### 4.1 单聊

| 旧前端调用 | 新中间层 | 说明 |
|---|---|---|
| `POST {网关}/chat` | `POST /v1/conversations/{id}/messages` | 请求体不带 history；返回 `reply` |
| `POST {网关}/chat/stream` | `POST /v1/conversations/{id}/messages:stream` | 帧：`delta {text}` / `done {seq,reply_seq}` / `error {code,message}` |
| `POST {网关}/chat/suggestions` | `POST /v1/conversations/{id}/suggestions` | **无请求体**；返回 `{suggestions[]}` |
| 图片挂在 `history[].image`（base64） | `POST /v1/attachments`（multipart `file`） | 只上传**当前轮**；历史图不重发 |
| 连接测试（发一条最小 /chat） | `GET /v1/meta` | 2xx 即连通，顺便显示能力位 |
| `CHARACTER_ID_MAP`（前端硬编码） | `GET /v1/characters`（启动后异步覆盖静态表） | 静态表保留，UI 同步路径要用 |

### 4.2 群聊（**已迁到 /v1**）

新后端把群聊收进了 `/v1`，这一版中间层已经全部改走新接口：

| 旧前端调用 | 新中间层 | 说明 |
|---|---|---|
| `POST /group/session` | `POST /v1/conversations`（`mode=group`、`members=[slug]`、`speak_mode`、`player_role`） | 建群；成员/身份/策略在这一刻定下 |
| `POST /group/reply` | `POST /v1/conversations/{id}/messages` 或 `…/next` | 玩家说话走 messages；"让下一位说"走 next |
| `POST /group/suggestions` | `POST /v1/conversations/{id}/suggestions` | 无请求体 |
| `POST /group/topic` | **没有对应端点** → 本地记录 + 会话里补一条 `generate=false` 的「新话题」提示行 | 见 §4.4 的话题说明 |
| `POST /group/session/close` | `DELETE /v1/conversations/{id}` | 软删；本地元数据一并清掉 |
| （新）发言权重 | `PUT /v1/characters/{slug}/weight` `{active:1..100}` | 只影响 `weighted` 模式 |

**四种发言策略**（`app/group.py`）：

| 模式 | 谁来说 | 本轮结束条件 |
|---|---|---|
| `weighted` **（建群默认）** | 按 `active_weight` 加权随机；被 @ 的人优先 | 全员各说一次（池空 → `done`） |
| `round` | 按成员顺序轮转 | 同上 |
| `smart` | 额外问一次主持人；她可以回 `END` 停聊 | `done=true` 或 `END` |
| `assign` | 玩家指定的那位 | 一次一条 |

界面里「轮流 / 加权 / 智能 / 指定」四个按钮就是这四个值；切换或改成员会
**作废当前会话**（`stores/chat.ts` 里 `groupSessionId = undefined`），下一回合
按新设置重建 —— 中间层只要在建群时如实传过去即可。

> 为什么 `weighted` 是默认：它不花额外的上游调用（不像 `smart` 要问一次主持人），
> 又比 `round` 自然 —— 这是新版群聊的主路径。权重用建群后弹出的
> **「发言权重」弹窗**调（见 §4.4）。

### 4.2.1 群聊的"一轮多人"怎么拼

服务端铁律：**一次请求只产生一条角色发言**。所以中间层在 `requestGroupReply` 里
做了两件事：

1. 玩家刚说完 → `POST /messages` 拿第一位；
2. `round` / `weighted` 再循环 `POST /next`，直到 `done=true`（上限 16 步防死循环），
   把这一轮所有发言一次性返回给界面。

界面层（`useGroupChat`）仍然拿到 `replies[]`，逐条带打字停顿显示 —— 与旧协议一致，
不需要改一行。

`smart` / `assign` 保持"一次一条"：`smart` 的 `done` 原样回给界面，由它的循环继续
（最多 200 轮，玩家随时可打断）；`assign` 拿一条就 `done=true`。

### 4.3 不发请求的旧概念

| 旧字段 | 处理 |
|---|---|
| `force_search` / `use_rag` | 新后端不做联网搜索（`capabilities.web_search=false`），忽略 |
| `use_new_prompt` | 新后端没有这个开关，忽略 |
| `character_prompt`（用户自定义人设覆盖） | 新后端没有对应入口；界面里仍可编辑，但**不会发给服务端**（见 05 §5） |
| `need_summary` / `context_window_tokens` / `summary_context` | v2 界面会带；新后端由服务端压缩，**忽略**这些字段，也不返回 `summary`（界面自动降级为本地裁剪，见 05 §6） |
| `system_prompt`（未收录角色） | 新后端只认已收录角色；未收录角色会明确报错 |

### 4.4 群聊的三件后勤：历史导入、话题、权重

**历史导入**：建群只建一条空会话；第一次 `requestGroupReply` 拿到界面历史后，
中间层用 `/v1/imports` 把整段历史（含每个说话人）导进去。导入会**新建**一条会话，
所以用一张别名表把界面手里的旧 id 指过去（`localStorage['baker_v1_group_alias']`），
之后所有请求自动跟着走，界面完全不知道 id 变了。

**话题**：新后端没有话题字段。中间层把它存进本地元数据，并在话题变化时往会话里
补一条 `generate=false` 的「【新话题】…」提示行；下一次玩家发言还会带一次
`【当前话题】…` 前缀。效果上模型能感知话题，但它会成为一条"玩家消息"进历史 ——
这是没有专用字段时能做到的最接近旧行为的方案。

**权重**：`PUT /v1/characters/{slug}/weight` 是**按账号/设备**的覆盖值，不是按群。
`GET /v1/characters` 只返回角色自带的默认值（后端没有"读我的覆盖值"端点），
所以弹窗显示顺序是：本地缓存（`baker_group_weights`）→ 服务端默认 → 50。
保存后立刻生效，下一次选人就按新权重抽。

## 5. 幂等、重试与"流式失败回退"

### 5.1 为什么需要跨两次调用的幂等键

`useAiChat` 的流式路径在"收到任何 delta 之前失败"时会**回退到非流式再请求一次**。
如果两次请求各生成一个 `client_msg_id`，服务端会把同一句话存两遍。

做法（`pendingTurns`）：

```
key = `${conversationId}|${history.length}|${text.slice(0, 80)}`
clientMsgId = pendingTurns.get(key) ?? 新生成
```

- 同一轮内的重试（网络、5xx、429）复用同一个 id；
- 流式失败 → 非流式回退，`history.length` 与 `text` 相同 → 同一个 id → 服务端回 `duplicate`；
- **成功之后清掉这个 key**：玩家再说同样一句话是新消息，不能永远复用旧 id。

### 5.2 `duplicate=true` 怎么处理

服务端对"存过的 client_msg_id"只回 `{seq, duplicate:true}`，**不带回复**。中间层：

1. `GET /v1/conversations/{id}/messages?after_seq={seq}`，取第一条 `side==='assistant'`
   —— 这是"请求其实成功了、响应丢在网络上"的情况，直接把回复捞回来；
2. 捞不到（说明上次存了用户消息但生成失败，例如撞 429）→ 调
   `POST /v1/conversations/{id}/continue` 补一条回复；
3. 连 `continue` 都不行（会话里一条助手消息都没有）→ 报一句
   "消息已保存，但生成失败，请稍后点重新生成"。

### 5.3 重试哪些、不重试哪些

| 情况 | 是否重试 | 说明 |
|---|---|---|
| 网络层失败（`TypeError`） | 是（最多 3 次） | 幂等键保证不会写重 |
| 429 / 502 / 503 / 504 | 是 | 优先按后端给的 `retry_after` 等（上限 30s） |
| `no_conversation` | 重建绑定后重试 1 次 | 见 §3.4 |
| 401 | `apiClient` 丢掉旧 token、重新注册设备后重放 1 次 | 只重放一次 |
| 流式已经出过字之后失败 | **不**重试 | 字已经显示，重发会重复 |
| 流式 `error` 帧 / 429 | **不**回退非流式 | 是服务端明确报错，不是链路问题 |

## 6. 图片：当前轮才发，历史图不重发

旧前端把 base64 图放在 `history[].image` 里，弱网/多图时请求体巨大，而且每一轮都会
把历史图重传一遍。新中间层：

1. 约定：**当前轮的图 = `history` 最后一条的 `image`**（`useAiChat.sendImage` 就是这么构造的，
   正文是 `[图片]`）；
2. 其余历史条目只保留文本（`[图片]` 占位）；
3. 当前轮先 `POST /v1/attachments`（6 MB 上限、只收 png/jpeg/webp/gif、按设备去重），
   拿到 `id` 后消息里只带 `attachment_id`；
4. 上传失败 → 这一轮退化成纯文字，不让整条消息发不出去；
5. 不会出现"历史图每轮重发"的问题 —— 请求体里根本没有 base64。

服务端取图要走 `attachment_url`（带归属校验），前端消息渲染仍用本地 dataURL，
不回显服务端的图；等做"服务端会话列表"时再一起接。

## 7. 错误形状与文案

新后端统一错误体：

```json
{ "error": { "code": "bad_credentials", "message": "用户名或密码不对", "details": {} },
  "request_id": "…" }
```

`apiClient.readError()` 转成 `ApiError`（`status / code / message / details / retryAfter`），
`friendlyError()` 负责给玩家看的中文：

| code | 显示 |
|---|---|
| `bad_credentials` | 用户名或密码不对 |
| `username_taken` | 这个用户名已经有人用了，换一个吧 |
| `device_taken` | 这台设备已经登录了另一个账号，请先登出 |
| `account_disabled` | 这个账号已被停用 |
| `too_many_attempts` | 尝试次数太多了，约 N 秒后再试 |
| `rate_limited`（429） | 服务繁忙（限速），约 N 秒后再试 |
| `no_character` | 没有收录「角色名」… |
| 其它 | 用后端给的 `message` |

群聊的老协议是**扁平错误体**（`{error:"…", code, retry_after, session_expired}`），
`groupBackend.postJson` 两种都认 —— 只认一种时会出现 `[object Object]`。

## 8. 地址解析

`src/constants/apiRoutes.ts`：

```
优先级：localStorage['baker_backend_url'] > VITE_BAKER_BACKEND > file:// 回退 127.0.0.1:5660 > 同源
v1Url(path)    = `${base}/v1${path}`
groupUrl(path) = `${base}/group${path}`
```

粘进来的地址如果带 `/v1`、`/chat`、`/group` 或末尾斜杠，会自动去掉 ——
这是最常见的粘错形态，不该表现为"所有请求 404"。

`backendUrl`（`ApiConfig` 里的旧字段）现在**不参与**解析：设置界面没有暴露它，
旧数据里也几乎都是空串；需要改地址请用上面三种方式。`resolveBackendUrl()` 保留同名导出。
