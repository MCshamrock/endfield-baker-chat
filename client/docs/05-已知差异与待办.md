# 已知差异与待办

> 这些不是"忘了做"，是这一版**有意留下**的边界。每条都写清：现象 / 原因 / 以后怎么补。
> 排序：影响用户感受的在前。

---

## 1. 表情/心情（mood）不再有独立 token

- **现象**：旧后端回 `{reply, mood: "sns_emoji_012"}`，头像旁的表情气泡会跟着变；
  新后端把表情**翻译成文字**（`[sns_emoji_012]` → `（疑惑）`）写进正文，不再单独下发 token。
- **影响**：消息文本里能看到「（疑惑）」；头像表情不再联动（没有数据）。
- **补法**（二选一，需后端配合）：
  - 后端在 `MessageCreatedOut` 里加 `mood` 字段（它本来就有 `messages.mood` 列）；
  - 或前端在中间层从正文尾部识别已知表情词反推 token（不推荐，容易误伤正文）。
- 倾向第一种：改动小、语义干净。

## 2. 一个角色 = 一条服务端会话，多段"存档"会共用上下文

- **现象**：原界面里一个干员卡下可以有多段子对话（存档），历史各自独立；
  新中间层按**角色**绑定服务端会话，所有子对话的消息都会进同一条服务端上下文。
- **原因**：界面的 `Conversation` 没有稳定 id（只有下标和名字），中间层拿不到"这是哪段存档"。
- **影响**：只有"一个角色开了多段存档"的玩家会感觉到（模型记得别的存档里的事）；
  单存档用户完全无感。
- **补法**：给 `Conversation` 加一个持久化 id（`crypto.randomUUID()`），
  `useAiChat` 构造 `BackendInput` 时带上，中间层把绑定键从 `role` 改成 `role + ':' + id`。
  这是**一次允许改界面的版本**才能做的事（要动 `types/chat.ts` / 持久化 / 导入合并）。

## 3. ~~服务端会话不在界面上展示~~ → **2026-11-18 已解决（P1）**

> **状态：已解决**。列表改成服务端驱动（`baker_list_source = server`），
> 领取取件码 / 注册带码 / 换设备登录之后，导入的会话会**立刻出现在左侧**，
> 点进去就能看到历史。下面的现象与补法保留，作为"当初为什么要这么改"的记录；
> 设计与验收见 [`07-服务端驱动列表.md`](07-服务端驱动列表.md)。

### 3.1 旧现象（改造前）

- **现象**：登录后（以及**用取件码领取之后**），服务端确实按账号归集了会话；
  但界面左侧列表仍然是本地卡库，**不会**列出"另一台设备聊出来的会话"。
  用户最容易踩的场景：新设备注册时填了取件码，注册成功、提示"已领取 N 段会话"，
  回到列表却是**空的** —— 他的结论会是"没成功"。
- **原因**：卡库是本地数据结构（导出/导入/多存档/群聊卡都在里面），
  左侧列表直接读 `chatStore.cards`；服务端会话（`GET /v1/conversations`）
  从来没有被写回这个结构。**"领取"只把数据写进服务端，不等于把条目写进列表。**
- **影响**：
  - 数据不丢：服务端在，换设备登录同一账号也在；
  - 领取后本地绑定会被清掉，下次和该干员聊天时中间层会绑到那条服务端会话、
    导入的历史作为上下文接上（**但界面里仍然看不到历史气泡**）；
  - 左侧列表不会多卡 —— **这一步需要"镜像"或"列表服务端驱动"**，见下面补法。
- **补法**（2026-11-18 用户已拍板 **B**）：
  1. **B：列表改为服务端驱动（已拍板，正解）** —— 列表数据源从 `chatStore.cards`
     换成 `GET /v1/conversations`，子卡直接带会话 id，点进去按 `/v1` 拉历史。
     设计稿见 [`07-服务端驱动列表.md`](07-服务端驱动列表.md)（含分期、验收、后端需求）。
  2. **A：镜像（已被否）** —— 把服务端会话镜像成本地卡条目。低成本，但本质还是
     "本地真相 + 一份拷贝"，跨设备仍要再同步一次；只打算用来救急的用户会以为
     数据没迁干净，所以不采用。
  3. **C：暂不处理** —— 领取后只有"服务端有数据 + 下次聊天接得上"，列表永远不长卡。
     这条已经不选。

> 结论（写给后来者）：**"领取成功" ≠ "列表里出现"。** 在 B 落地之前，
> 领取只能保证"服务端有数据 + 下次聊天接得上"，界面上不会自己长出卡片。
> B 的 P1 一期就能兑现"领取后立刻可见"，见 `docs/07 §4`。

## 4. 群聊已迁到 `/v1`，但话题是"模拟"的

- **状态**：建群 / 发言 / 下一句 / 推荐 / 关群都走 `/v1`；`round`、`weighted`、
  `smart`、`assign` 四种策略都能用；建群后弹「发言权重」。
- **话题**：新后端没有话题字段。现在是「本地记录 + 往会话里补一条 `generate=false`
  的【新话题】提示行 + 下一条玩家消息带【当前话题】前缀」。模型能感知，但它会作为
  一条玩家消息进历史（而不是独立的 system 段）。
- **补法**：`/v1` 加 `topic` 字段（`conversations.topic` 或 group settings），
  中间层把模拟逻辑删掉即可。
- **权重读取**：`GET /v1/characters` 只给角色默认 `active_weight`，没有"读我的覆盖值"
  的端点；弹窗靠本地缓存显示。补法：`GET /v1/characters/weights` 或让
  `/v1/characters` 带上当前 owner 的覆盖值。

## 5. 用户自定义人设 / 世界观 / 提示词覆盖，不再影响后端回复

- **现象**：设置里仍能编辑「提示词覆盖」「世界观背景」，但新后端只按 `character_id`
  读服务端自己的人设；这些前端字段发不过去。
- **原因**：新后端把提示词收归服务端（这是重写的目标之一），没有"客户端覆盖人设"的入口。
- **影响**：自定义 API 模式（`apiMode === 'custom'`）下这些设置**仍然生效**（直连用户自己的 API）；
  默认模式下不生效。
- **补法**：后端加 `device_prompts` 的写接口（表已经有了：`device_prompts`，导入老包时会写），
  中间层把覆盖内容同步过去。

## 6. ~~默认模式下前端还在跑一条"假总结"链~~ → **2026-11-18 已删除（P0）**

> **状态：已删除**。删掉的是：`shouldRequestBackendSummary`、请求体里的
> `need_summary` / `summary_context`、等 summary 的状态、等不到就本地裁剪、
> `applyBackendSummary`、"总结失败，已跳过"那条降级。
> **保留**：自定义 API 模式的 `applyCustomSummary`、手动压缩（默认模式下已不暴露入口）。
> 下面的清单是删除前的记录。

### 6.1 旧现象（改造前）

- **现象**：v2 界面按"提示词 + 历史 ≥ 131072 × 45~80%"判定该总结了，就发
  `need_summary=true` 并锁住输入框显示"正在整理记忆…"；新后端**忽略**这个字段
  （它自己每轮压：20 万预算、80% 触发、压到 50%、只压不裁），所以永远等不到 `summary`
  → 走失败分支：本地把历史**整轮裁到 60%** + 提示"总结失败，已跳过"。
- **原因**：总结已经是服务端职责（`app/memory.py` `compress_to_fit`，
  `app/generate.py:276/583`）。前端这套是**老客户端/自定义 API** 的机制，搬进 `/v1` 链路
  就变成第二条压缩链（`功能全集.md:385/489`）。
- **影响**：聊天能继续，但用户会看到一次假等待 + "总结失败"，并且本地**提前裁掉**了
  服务端本来只会压缩的上下文 —— 是净损失，不是降级。
- **修法**：不是让后端补 `/summarize`（那会变成两条链），而是**默认模式这条链直接删**：
  判据、`need_summary` 字段、等待状态机、失败后的本地裁剪。
  清单与验收见 [`08-总结与压缩归属.md`](08-总结与压缩归属.md) §2/§4，排期在 P1 之后。
- **保留**：自定义 API（`applyCustomSummary`）与旧版直连（`applySmartSummary`）仍用前端总结；
  手动「压缩上下文」也不动。

## 7. 设置里的「默认 / 备用」路线现在是死控件

### 领取的数据为什么会"看不到"

领取 = 后端把包导入成**服务端会话**（和 `/v1/imports` 同一件事）。当前界面左侧列表
仍是这台设备的**本地存档**（见 §3），所以：

- 数据确实在账号名下，换设备登录同一账号也在；
- 但列表里不会多出一张卡 —— 下次和对应干员聊天时，中间层会绑定到刚导入的那条会话，
  导入的历史作为上下文接上；
- 领取成功后我们会清掉本地「角色 → 会话」绑定（`baker_v1_bindings`），
  否则下一句话会接在旧的空会话上，等于"领了却看不见"。

要让导入的会话真的出现在列表里，得先做 §3 的 B（列表服务端驱动，设计见 `docs/07-服务端驱动列表.md`）。

## 9. 设备注册字段与后端列宽

- `devices.platform / app_ver / os_ver` 是 `VARCHAR(32)`、`tz 64`、`locale 16`。
- 前端已经按列宽截断（`os_ver` 只写 `Windows 10/11` 这类短名），所以不会 500。
- 建议后端把 `os_ver` 放宽到 255，并在入口统一截断 —— 否则别的老客户端塞长 UA 仍会 500。

## 10. 没有找回密码

- 前端不提供"忘记密码"入口，避免给了入口却没人处理。
