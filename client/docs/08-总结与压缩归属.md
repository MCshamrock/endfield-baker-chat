# 08 · 总结与压缩的归属（新 web 不做客户端总结）

> 状态：2026-11-18。原计划把线上 3.1 的前端「智能总结」整套移植到 3.2.2 界面，
> 核查后**撤回**：新后端已经自己做压缩/总结，前端再搬一遍是重复造轮子，
> 而且两条压缩链会互相打架（`功能全集.md:385`、`:489`）。
>
> 本文只回答一个问题：**谁负责压缩/总结？** 附一份"前端现在还在偷偷做"的清单。
> 代码清单**只列不改**（按 lead 要求），统一放到 P1 之后处理。

---

## 1. 结论三条

### 1.1 新 web 走 `/v1` 时，不做任何客户端总结/压缩

服务端已经有一整条压缩链，每轮生成前自动跑：

| 环节 | 位置 | 做什么 |
|---|---|---|
| 入口 | `app/generate.py:276`（单聊）/ `:583`（群聊） | 每轮生成前调 `memory.compress_to_fit` |
| 压缩器 | `app/memory.py:74` `compress_to_fit()` | 把最老一段原文压成"前情提要"，**只压缩不裁切**（原文还在库里，只是不再发） |
| 预算 | `app/prompt/budget.py` `history_budget()` | 历史额度 = 总预算 − 固定前缀 − 给回复留的余量 |
| 参数 | `app/settings.py:127-144` | 预算 200k、80% 触发、压到 50%、每次切 30k、保留最近 4 轮原文、最多 8 轮 |

`app/settings.py` 的实际数字（前端常量已经对不上了，见 §2 的 C）：

```
prompt_budget_tokens = 200_000      # 总预算
reply_reserve_tokens = 4_096        # 回复余量
compress_at_ratio    = 0.8          # 80% 触发
compress_to_ratio    = 0.5          # 压到 50%
compress_chunk_tokens= 30_000       # 单次切 30k
compress_max_rounds  = 8            # 最多 8 轮；撞上限宁可超预算也不裁
keep_recent_turns    = 4            # 最近 4 轮原文必须留着
```

为什么必须只留一条链：压缩会改写"发出去的历史"。两条链各改一次，前缀就不稳定，
上游缓存命中率会莫名下降，而且"到底是谁把这段丢了"永远定位不到
（`功能全集.md:385` 与 `:489`；`功能全集.md:511` 也把"压缩/摘要"列在"必须搬去服务端"）。

### 1.2 新 web 不要调用本地 summary 逻辑，也不要调 `/api/legacy-key`

- 用户已定**不补** `/api/legacy-key` 端点。
- 前端唯一的调用点是 `src/utils/llm.ts:35` 的 `fetch('/api/legacy-key')`，
  它经由 `stores/settings.ts:699-720` 的 `getSummaryApi()` 默认分支被**群聊总结**间接用到
  （见 §2 的 B）。新后端没有这个端点 → 404 → 白等一次超时后降级。

### 1.3 老客户端继续用它自己的总结，服务端只做透传

- `app/api/legacy.py:69` 收 `summary_context`，`:196` 把它当 `summary` 塞进提示词。
- 原因：老客户端（EXE/APK）是**无状态**的（每轮自己带完整 history），
  它的总结只能在客户端生成；服务端不接管，只负责"你给你的摘要，我放进提示词"。
- 新 web 走 `/v1` 有状态会话，**不需要**这个字段（前端也不要再发 `need_summary`）。

## 2. 前端死路径清单（只列，先别删）

> 判定标准：新 web 在**默认模式（`apiMode === 'backend'`）**下仍会执行、
> 但新后端并不需要它的逻辑。P1 之后统一处理（§4）。

### A. 单聊：后端模式仍会发"假总结请求"，失败后还本地裁历史

| 位置 | 做什么 |
|---|---|
| `src/composables/useAiChat.ts:415-450` | `shouldRequestBackendSummary()` —— 判据**只对 backend 模式**成立（`settingsStore.apiConfig.apiMode !== 'backend'` 直接 false） |
| `src/composables/useAiChat.ts:724-736` | 判据为真 → 请求带 `need_summary=true`，并 `chatStore.beginSummaryWait(sub)` 锁输入、显示"正在整理记忆…" |
| `src/utils/backend.ts:86/90`、`:347-353` | 请求体写入 `need_summary` / `summary_context`（新后端**忽略**这两个字段） |
| `src/composables/useAiChat.ts:1161-1180` | 服务端当然不会回 `summary` → 走失败分支：`planRoundTrim()` **本地整轮裁剪到 60%** + `noteSummaryFailure()` 弹"总结失败，已跳过" |
| `src/stores/chat.ts:1080-1200`、`:1342` | 总结等待/失败状态机、`applyBackendSummary()`（只有服务端真回 summary 才会走，新后端不会） |
| `src/components/chat/ChatInput.vue:37`、`:927` | 输入框上方的"正在整理记忆…"提示读的是同一份等待状态 —— A 触发时用户会真的看到它 |

**用户感知**：聊到一定长度（前端以为的 131072 窗口，见 C）时，发消息会多等一拍、
输入框短暂上锁，然后出现"总结失败，已跳过"；同时本地历史被裁掉一段 ——
而服务端本来只会"压缩不裁切"。这是**净损失**。

### B. 群聊：后端模式仍会调外部总结 API（并顺手打 `/api/legacy-key`）

| 位置 | 做什么 |
|---|---|
| `src/composables/useGroupChat.ts:406-438` | `historyForRequest()`：历史 > `BACKEND_HISTORY_LIMIT`（=30；注释里的"50"是旧值）且开关开着 → `settingsStore.getSummaryApi()` → `requestSummary()`（`utils/summary.ts`） |
| `src/stores/settings.ts:699-720` | `getSummaryApi()` 在 backend/legacy 分支 → `fetchLegacyApiKey()`（`utils/llm.ts:35`） |
| `src/utils/summary.ts` | 一次 OpenAI 兼容 `/chat/completions` 调用（默认 20s 超时） |

**用户感知**：群聊长了以后，每回合先打一次 `/api/legacy-key`（新后端 404），
再降级成"最近 50 条"；慢，且群里模型看到的上下文比单聊更少。

### C. 常量过期（会放大 A）

- `src/constants/summaryBudget.ts:36` `BACKEND_PROMPT_TOKENS = 4000`
- `src/constants/summaryBudget.ts:44` `BACKEND_CONTEXT_WINDOW_TOKENS = 131072`
- 服务端现在是 **200k 预算 / 80% 触发**（`app/settings.py:127-132`）。

前端按 131072 算阈值，比服务端**早得多**就误判"该总结了" → 更容易触发 A 的假请求。
（这条本身就是 `功能全集.md:204` 的 MEM-04："窗口写死 131072、提示词写死 4000"。）

### D. 设置页：开关与滑条在默认模式下仍可调

- `src/components/layout/SettingsDialog.vue` 的「智能总结」区块（`SetSection title="智能总结"`，约 `2145` 起）。
- 本轮已改文案（§3）：默认模式下提示"由服务端自动处理"，并隐藏只对前端链路有意义的
  「运行参数 / 精细度调整」两块；开关保留（切到自定义 API 还要用）。

### E. 保留不动（不是死路径）

| 路径 | 为什么保留 |
|---|---|
| `useAiChat.ts:407` `applySmartSummary` + `utils/summary.ts` + `utils/summaryTrim.ts` | **旧版直连（legacy）** 自己的压缩链 |
| `useAiChat.ts:355` `applyCustomSummary` + `utils/customSummary.ts` + `utils/summaryThreshold.ts` | **自定义 API** 的前端总结（45–80% 动态阈值仍有效） |
| 用量面板「压缩上下文」+ `useContextCompaction` | **手动**压缩（`功能全集.md:203` MEM-02 判"保"），与自动总结无关，别一起删 |

## 3.5 默认模式不暴露「压缩上下文」入口（2026-11-18 P0 已落地）

默认模式（`apiMode === 'backend'`）下，用量面板里的**手动「压缩上下文」按钮直接隐藏**
（不是置灰）：服务端每轮自己压，前端没有总结端点，点了只会拿到一句报错。
面板里改为一句说明「默认模式由服务端每轮自动压缩（只压不裁），这里不需要手动压缩」。

`custom` 模式**保留**这颗按钮 —— 那里的总结仍是客户端做的（`useContextCompaction` →
`getSummaryApi()` → 用户自己的 OpenAI 兼容端点）。

## 4. 留给 P1 之后的动作（不在本轮）—— ✅ A/B/C 已于 2026-11-18 P0 完成

1. 给 A 的两处加闸门：`shouldRequestBackendSummary` 直接返回 false（或删掉 backend 分支），
   请求不再写 `need_summary`；`beginSummaryWait` / 失败后的 `planRoundTrim` 一起删。
   验收：`adapter-e2e` 抓请求体，断言**没有** `need_summary`；聊天到长历史不再出现"总结失败"。
2. 给 B 加闸门：`historyForRequest` 只在 `apiMode === 'custom'` 时才调 `getSummaryApi`；
   或者干脆让群聊历史 > 50 条也原样交给服务端（服务端本来会压）。
   验收：群聊历史 > 30 条发消息时网络面板**没有** `/api/legacy-key`。
3. C 的常量：后端模式下不再需要（随 A 一起删）；若保留设置页展示，改成读服务端参数（或删展示）。
4. 与 P1 的顺序：**先 P1（列表服务端化）→ 再清这里**。理由见
   [`07-服务端驱动列表.md`](07-服务端驱动列表.md) 的「与总结/压缩清理的先后」一节。

> 提醒后来者：**"服务端会压缩"不等于"前端那个开关没用了"** ——
> 开关在自定义 API 模式下仍然要工作。清理时只能按 `apiMode` 分支删，不能整块删。
